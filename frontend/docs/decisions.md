# 프론트엔드 결정 기록

프론트에서 무엇을 왜 골랐고 왜 뺐는지 남기는 문서입니다. 같은 논의를 다시 하지 않도록, 도구나 구조를 바꾸기 전에 여기를 먼저 확인합니다.

기록 규칙은 세 가지입니다.

- 새 결정은 맨 아래에 번호를 이어서 추가합니다.
- 결정이 바뀌어도 기존 항목은 지우지 않습니다. 제목 앞에 `[대체됨 → D번호]`를 붙이고 새 항목을 추가합니다.
- "다시 볼 조건"이 생기면 그 항목부터 다시 검토합니다.

## D1. 프론트는 `frontend/` 안에서만 관리한다

- **날짜**: 2026-10-19
- **결정**: 프론트는 `frontend/`에 독립된 앱으로 두고 자체 `package.json`, lockfile, 설정 파일을 가집니다. 레포 루트 파일은 수정하지 않습니다.
- **이유**: 레포 루트와 팀 공용 설정(`docs/`, `.github/`, 루트 `.gitignore` 등)은 팀장이 관리합니다. 루트에 `package.json`이 없으면 백엔드와 AI 팀원이 Node 없이 작업할 수 있습니다.
- **검토한 대안**: Turborepo, Nx, pnpm workspace. JS 패키지만 관리하는 도구라 JS 앱이 하나인 지금은 필요 없습니다.
- **다시 볼 조건**: JS 앱이나 공유 TS 패키지가 두 개 이상 생길 때

## D2. Vite + React + TypeScript로 만든다

- **날짜**: 2026-10-19
- **결정**: 빌드 도구는 Vite, UI는 React, 언어는 TypeScript(strict)입니다.
- **이유**: SSR이나 SEO가 필요 없습니다. 빌드 결과가 정적 파일이라 배포가 단순합니다.
- **검토한 대안**: Next.js. Node 서버가 하나 더 필요하고 배포 구성이 복잡해집니다.
- **다시 볼 조건**: 검색 노출이나 서버 렌더링이 요구사항에 들어올 때

## D3. 패키지 매니저는 npm, Node는 24로 고정한다

- **날짜**: 2026-10-19
- **결정**: npm을 쓰고 lockfile을 커밋하며, 설치는 `npm ci`로 합니다. `engines`(`>=24 <25`)와 `.npmrc`의 `engine-strict=true`로 다른 Node 버전에서는 설치가 실패하게 합니다.
- **이유**: npm은 Node에 포함되어 있어 따로 설치할 것이 없습니다. 팀원마다 Node 버전이 다르면 lockfile이 계속 바뀝니다.
- **검토한 대안**: pnpm. 더 빠르지만 팀원 PC와 CI에 corepack 설정이 추가됩니다.

## D4. Lint는 Oxlint 대신 ESLint를 쓴다

- **날짜**: 2026-10-19
- **결정**: ESLint + typescript-eslint + react-hooks + react-refresh를 씁니다. Vite 공식 템플릿(`--eslint`) 설정을 그대로 가져왔습니다.
- **이유**: 팀원 대부분이 써 봤고 자료가 많으며 플러그인을 모두 쓸 수 있습니다. 이 규모 프로젝트에서는 속도 차이가 크지 않습니다.
- **검토한 대안**: Oxlint(create-vite 9의 기본값). 빠르지만 일부 플러그인이 없습니다.
- **참고**: shadcn 컴포넌트는 variants를 컴포넌트와 같이 export하므로 `src/components/ui/`에서만 `react-refresh/only-export-components`를 끕니다.

## D5. 포매터는 Prettier, 작은따옴표에 세미콜론 없음

- **날짜**: 2026-10-19
- **결정**: Prettier에 `semi: false`, `singleQuote: true`, Tailwind 클래스 정렬 플러그인을 씁니다. `package-lock.json`은 포맷 대상에서 뺍니다.
- **이유**: Vite 템플릿 스타일과 같아서 기존 파일이 가장 적게 바뀝니다. lockfile을 Prettier가 고치면 npm이 다시 되돌려서 diff가 계속 생깁니다.
- **참고**: `eslint-config-prettier`는 넣지 않았습니다. 지금 ESLint 추천 설정에는 Prettier와 충돌하는 포맷 규칙이 없습니다.

## D6. 스타일링은 Tailwind CSS, UI 컴포넌트는 shadcn/ui

- **날짜**: 2026-10-19
- **결정**: 스타일은 Tailwind 유틸리티 클래스로 씁니다. 버튼, 입력, 다이얼로그 같은 UI는 shadcn/ui(Radix, nova 프리셋)에서 필요한 것만 `npx shadcn add`로 가져옵니다.
- **이유**: 간격과 색상이 정해진 값 안에서만 쓰여 팀원마다 스타일이 갈라지지 않습니다. shadcn은 소스가 레포에 복사되어 AI가 읽고 고칠 수 있고, AI가 화면마다 다른 컴포넌트를 새로 만들지 않고 같은 컴포넌트를 재사용합니다.
- **검토한 대안**: CSS Modules. 의존성이 없지만 공통 값을 따로 관리해야 하고 작성 방식이 사람마다 달라집니다.
- **다시 볼 조건**: 디자인 시스템이 정해지면 테마 토큰(색, radius)과 한글 폰트를 바꿉니다. 기본 폰트 Geist에는 한글이 없습니다.

## D7. 상태와 API 호출은 TanStack Query, Zustand, axios로 나눈다

- **날짜**: 2026-10-19
- **결정**: 서버에서 받은 데이터는 TanStack Query로만 관리합니다. 서버와 상관없는 화면 상태 중 여러 컴포넌트가 공유하는 것만 Zustand에 둡니다. API 요청은 `src/api/client.ts`의 axios 인스턴스(`baseURL: /api`) 하나로만 보냅니다.
- **이유**: 캐싱, 로딩, 에러, 재요청을 직접 구현하지 않아도 됩니다. 인증 헤더나 공통 에러 처리를 고칠 곳이 한 군데로 모입니다.
- **검토한 대안**: fetch 래퍼. 의존성은 없지만 interceptor와 타임아웃을 직접 만들어야 합니다.

## D8. 라우팅은 React Router의 `createBrowserRouter`

- **날짜**: 2026-10-19
- **결정**: React Router 8의 data router(`createBrowserRouter` + `RouterProvider`)를 쓰고, 라우트는 `src/router.tsx` 한 곳에 정의합니다. 무거운 페이지는 route `lazy`로 분리합니다.
- **이유**: route 단위 코드 분할이 기본으로 됩니다. 3D 페이지처럼 큰 화면을 첫 번들에서 뺄 수 있습니다.
- **검토한 대안**: React Router framework 모드. 파일 기반 라우팅과 SSR 기능이 있지만 빌드 구성이 바뀌고 지금은 필요 없습니다.

## D9. API 응답과 폼 입력은 Zod로 검증한다

- **날짜**: 2026-10-19
- **결정**: API 응답은 Zod 스키마로 `parse`한 뒤 쓰고, 타입은 `z.infer`로 스키마에서 뽑습니다. 폼은 React Hook Form + `zodResolver`로 만들고 검증 규칙은 스키마에만 씁니다.
- **이유**: TypeScript 타입은 실행 중에 확인되지 않습니다. 바이브 코딩으로 만든 코드가 실제 응답 형태와 어긋나면 그 자리에서 에러로 드러나야 합니다.
- **다시 볼 조건**: 백엔드 OpenAPI에서 Zod 스키마를 자동 생성하게 되면 손으로 쓰는 스키마를 생성 코드로 바꿉니다.

## D10. 백엔드의 snake_case 응답을 변환하지 않는다

- **날짜**: 2026-10-19
- **결정**: 백엔드 JSON 키가 snake_case(`started_at`)이므로 Zod 스키마와 타입의 키도 snake_case 그대로 씁니다. camelCase로 변환하지 않습니다.
- **이유**: 변환 코드가 없어 단순합니다. OpenAPI에서 생성한 타입을 그대로 쓸 수 있습니다.
- **검토한 대안**: axios interceptor에서 변환하는 방법은 생성된 타입과 키가 어긋나고 깊은 객체에서 예외가 생깁니다. Zod `transform`은 스키마마다 변환 코드가 늘어납니다.
- **다시 볼 조건**: 백엔드와 최종 확인 전입니다. 백엔드가 camelCase로 바꾸기로 하면 이 결정을 대체합니다.

## D11. 테스트는 Vitest + React Testing Library, E2E는 Playwright

- **날짜**: 2026-10-19
- **결정**: 로직과 입력 컴포넌트는 Vitest + RTL로, 실제 화면은 Playwright(Chromium)로 테스트합니다. 지금은 화면이 뜨는지 보는 스모크 테스트 1개만 있습니다.
- **이유**: 바이브 코딩에서는 AI가 쓴 코드가 맞는지 자동으로 확인하는 장치가 필요합니다. 단위 테스트는 라우팅이나 실제 렌더링 문제를 잡지 못해서 E2E도 함께 둡니다.
- **참고**: 3D 화면은 픽셀 비교를 하지 않습니다. 캔버스가 보이는지와 콘솔 에러가 없는지까지만 확인합니다. 테스트가 실패하면 테스트를 지우거나 기대값을 바꿔서 통과시키지 않고 코드를 고칩니다.

## D12. 3D는 three.js + React Three Fiber

- **날짜**: 2026-10-19
- **결정**: WebGL 3D는 three.js를 React Three Fiber로 씁니다. `<Canvas>`가 들어간 컴포넌트는 반드시 lazy로 불러옵니다.
- **이유**: React 컴포넌트처럼 씬을 작성할 수 있습니다. three.js 청크가 약 912 KB라 첫 화면 번들에 넣으면 안 됩니다.
- **다시 볼 조건**: 압축 모델 로딩이나 카메라 컨트롤이 필요해지면 `@react-three/drei`를 추가합니다. React를 19.4 이상으로 올리기 전에 R3F 지원 여부를 확인합니다.

## D13. 프론트는 Docker 없이 정적 파일로 배포한다

- **날짜**: 2026-10-19
- **결정**: 프론트 Dockerfile과 nginx 설정을 두지 않습니다. CI는 `npm ci && npm run check`로 검사와 빌드를 하고 결과물 `dist/`를 배포합니다.
- **이유**: 빌드 결과가 정적 파일이라 컨테이너가 없어도 됩니다. 서빙하는 서버 한 곳에서 SPA fallback과 `/api` 프록시를 함께 처리할 수 있습니다.
- **검토한 대안**: node 빌드 + nginx 서빙 이미지. 처음에는 이 방식으로 세팅했다가 뺐습니다.
- **다시 볼 조건**: 팀이 모든 서비스를 컨테이너로 배포하기로 하면 다시 추가합니다(10줄 정도).

## D14. Git hook 도구는 프론트에서 따로 넣지 않는다

- **날짜**: 2026-10-19
- **결정**: Husky, lint-staged, commitlint를 넣지 않습니다.
- **이유**: Git hook 경로는 레포 전체에 하나뿐이라 프론트만 따로 넣으면 다른 앱의 hook과 충돌합니다. 팀이 Jira 키 자동 삽입용 `prepare-commit-msg` hook을 도입할 예정입니다.
- **다시 볼 조건**: 팀 공용 hook이 도입될 때 프론트 검사(`npm run check`)를 거기에 붙일지 같이 정합니다.

## D15. 도입하지 않거나 미룬 도구

- **날짜**: 2026-10-19
- **Storybook**: 도입하지 않습니다. 짧은 프로젝트에서는 세팅과 유지 비용에 비해 얻는 것이 적습니다.
- **MSW**: API를 부르는 컴포넌트 테스트가 많아지면 검토합니다. 지금은 단위 테스트는 `vi.mock`, E2E는 `page.route`로 대체합니다.
- **md 부분 편집 기능**: 요구사항이 정해지면 블록 단위 편집(`react-markdown` + `mdast-util-from-markdown`)을 검토합니다.
- **AI 서버 직접 호출**: 하지 않습니다. 인증과 키 관리를 위해 백엔드를 거칩니다.

## D16. 기존 3D geometry를 보존하고 Canvas의 renderer를 주입한다

- **날짜**: 2026-10-23
- **결정**: 도시, 사무실, 실외 엔진의 기존 geometry·레이아웃·이동·카메라 계산을 유지합니다. 각 엔진은 선택적인 외부 `WebGLRenderer`를 받고, R3F Canvas의 `gl`을 공유합니다. `useFrame` 우선순위 1로 자동 렌더링을 인계받아 기존 렌더링 순서를 실행합니다.
- **이유**: 형상을 새로 작성하면 기존 부지, 가구, 캐릭터, 출입구, 가림 처리와 클릭 판정이 달라질 수 있습니다. renderer를 공유하면 Canvas마다 WebGL 컨텍스트가 하나로 유지됩니다.
- **소유권**: 외부 renderer의 canvas 삽입·제거, 크기·픽셀 비율 설정, renderer dispose·context loss는 Canvas가 맡습니다. 엔진은 자신이 만든 scene 자원을 정리합니다.
- **검사**: 기존 배치·이동 회귀와 외부 renderer 소유권 검사를 Vitest로 유지하며, WebGL 진입은 Chromium에서 확인합니다.

## D17. 브라우저 예시를 기본으로 하고 REST 계약 경계를 준비한다

- **날짜**: 2026-10-23
- **결정**: `VITE_API_MODE=mock`을 기본으로 사용하고 `live`일 때만 `/api`를 호출합니다. 명세의 108개 REST 경로와 요청·응답 스키마를 서비스 계층에 등록합니다. 예시 환경은 axios 어댑터로 처리하며 실제 네트워크로 대체 호출하지 않습니다.
- **이유**: 백엔드를 수정하거나 가동하지 않고도 프론트 흐름을 검토할 수 있고, 실제 연동 때도 같은 서비스 경계를 사용할 수 있습니다. 예시 값과 실제 AI·에이전트 활동을 구분해야 합니다.
- **참고**: 실제 백엔드 통합은 아직 검증하지 않았습니다. 인증·CSRF 및 세부 계약 확정 후 live 모드로 별도 검증해야 합니다. D15의 MSW 미도입 결정은 유지합니다.

## D18. API에 없는 공간 설정은 브라우저에 보관한다

- **날짜**: 2026-10-23
- **결정**: 사용자가 고르는 부지·외관과 시점 설정은 Zustand persist로 브라우저에 보관합니다. 부지·외관은 계정과 프로젝트 ID를 함께 키로 사용합니다. 프로젝트 이름·설명·멤버십 등 서버 데이터는 Query에서 읽습니다.
- **이유**: 현재 프로젝트 REST에는 부지·건물 저장 필드가 없습니다. 3D 선택 기능을 유지하기 위해 서버 계약을 임의로 늘리지 않습니다.
- **제한**: 브라우저 저장값은 다른 기기와 동기화하지 않습니다.
- **다시 볼 조건**: 팀이 공간 저장 API와 계정별 배치 정책을 확정할 때

## D19. 미정 content와 Git 확장 계약을 만들어 내지 않는다

- **날짜**: 2026-10-23
- **결정**: 세부 스키마가 미정인 구조화된 `content`는 JSON 객체 경계까지 검증합니다. Git·PR 등 요구사항에 있으나 REST 계약이 없는 확장은 상태 안내를 제공하고 실제 연결·게시 API를 임의로 호출하지 않습니다.
- **이유**: 프론트 내부에서 만든 형식을 확정된 팀 계약처럼 사용하면 실제 연동 시 의미와 필드가 어긋납니다. 문서 원문·버전·근거를 확인하는 흐름과 미정 구조를 분리해 유지합니다.
- **다시 볼 조건**: OpenAPI, content 스키마, Git 저장소·PR 인증 및 조회·게시 계약이 확정될 때

## D20. 공간 이동과 설계 승인 상태를 분리한다

- **날짜**: 2026-10-24
- **결정**: 프로젝트 준비 단계에서도 사무실의 보이는 바닥을 걸을 수 있다. 기준 설계 발행 여부는 업무 승인 절차에만 사용한다. 시점 전환과 업무 창 닫기 뒤에는 사무실 입력 포커스를 복원하고, 업무 창이 열려 있으면 이동 입력을 비운다.
- **이유**: 문서를 아직 등록하지 않은 프로젝트에서도 기존 3D 이동 기능을 사용할 수 있어야 한다. 입력창을 편집하는 동안의 WASD 입력은 캐릭터에게 전달하지 않는다.
- **검사**: 준비·발행 단계의 충돌 없는 출발점을 단위 검사하고, 1·3인칭 전환 직후 이동과 업무 창 입력·복귀를 Chromium에서 실제 위치 변화로 확인한다.

- **날짜**: 2026-10-30
- **결정**: 팀원 캐릭터는 Kenney Mini Characters 5종, 도시·창밖 건물은 Kenney City Kit 모델을 `public/models/kenney/`에 두고 three의 `GLTFLoader`(이미 있는 three 안의 기능)로 읽는다. 팩마다 `Textures/colormap.png`와 `License.txt`를 같이 둔다. 비비는 사용자 캐릭터 시트 그대로 둔다. 계정 avatar 저장값(`bee-*`)은 그대로 쓰고 화면 이름과 모델만 바꿨다.
