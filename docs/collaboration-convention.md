# GitHub & Jira 협업 컨벤션

## 1. 기본 운영 원칙

| 구분 | 용도 |
| --- | --- |
| **GitHub** | 코드 관리, PR, 코드 리뷰, 외부 Issue 관리 |
| **GitLab** | GitHub 코드의 자동 동기화 저장소 |
| **Jira** | 내부 팀원의 작업 및 일정 관리 |

- 내부 팀원은 **Jira**, 외부 기여자는 **GitHub Issues**를 사용한다.
- 모든 코드 변경은 PR과 코드 리뷰를 거쳐 반영한다.
- GitHub를 기준 저장소로 사용하며, GitLab에는 직접 개발 내용을 반영하지 않는다.
- 외부 Issue를 내부 개발 일정에 반영할 경우 Jira 티켓을 생성하고 연결한다.

## 2. Jira 컨벤션

### 작업 구조

**Epic → Story / Task / Bug → Sub-task**

| 유형 | 설명 | 예시 |
| --- | --- | --- |
| Epic | 대단위 기능 | 회원 시스템 구축 |
| Story | 사용자 관점의 기능 | 카카오 로그인 구현 |
| Task | 기술 및 개발 작업 | 로그인 API 구현 |
| Bug | 오류 수정 | 토큰 만료 오류 |
| Sub-task | 세부 개발 작업 | OAuth 콜백 처리 |

### 작성 규칙

- 제목은 작업 목적이 드러나도록 구체적으로 작성한다.
- 작업 내용과 완료 기준을 명시한다.
- 큰 작업은 독립적으로 개발 및 검증할 수 있는 단위로 나눈다.
- 하나의 작업 브랜치와 PR은 하나의 Jira 티켓을 기준으로 하는 것을 원칙으로 한다.
- 작업 상태는 **해야 할 일 → 진행 중 → 완료**로 관리한다.
- `dev` 병합 및 완료 기준 충족 후 티켓을 완료 처리한다.

## 3. Branch 컨벤션

### 브랜치 이름

`<타입>/<작업영역>-<기능명>-<티켓번호>`

**내부 팀원**

```
feature/backend-login-S15P31A108-123
feature/frontend-dashboard-S15P31A108-124
fix/backend-auth-S15P31A108-125
```

**외부 기여자**

```
feature/backend-login-42
fix/frontend-button-43
```

외부 기여자는 GitHub Issue 번호가 없는 경우 생략할 수 있다.

### 브랜치 타입

| 타입 | 설명 |
| --- | --- |
| `feature` | 새로운 기능 개발 |
| `fix` | 버그 수정 |
| `refactor` | 코드 리팩토링 |
| `docs` | 문서 수정 |
| `test` | 테스트 작성 및 수정 |
| `chore` | 환경 설정 및 기타 작업 |

### 작업 영역

| 영역 | 명칭 |
| --- | --- |
| 프론트엔드 | `frontend` |
| 백엔드 | `backend` |
| AI | `ai` |
| 인프라 및 CI/CD | `infra` |
| 공통 | `common` |

### 작성 규칙

- 영문 소문자와 하이픈(`-`)을 사용한다. 단, Jira 티켓 키는 대문자를 유지한다.
- `FE`, `BE` 대신 `frontend`, `backend`를 사용한다.
- 내부 팀원은 브랜치 마지막에 Jira 티켓 번호를 필수로 작성한다.
- 작업 브랜치는 최신 `dev`에서 생성하고 병합 후 정리한다.

## 4. Commit Message 컨벤션

### 커밋 메시지 구조

`타입: 작업 내용 (티켓번호)`

**내부 팀원**

```
feat: 카카오 로그인 API 구현 (S15P31A108-123)
fix: 로그인 토큰 만료 오류 수정 (S15P31A108-124)
refactor: 에이전트 응답 처리 로직 개선 (S15P31A108-125)
```

**외부 기여자**

```
feat: 로그인 기능 개선 (#42)
fix: 버튼 클릭 오류 수정 (#43)
```

### 커밋 타입

| 타입 | 설명 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `design` | UI 및 CSS 변경 |
| `text` | 텍스트 및 오타 수정 |
| `refactor` | 코드 구조 개선 |
| `comment` | 주석 추가 및 수정 |
| `docs` | 문서 수정 |
| `test` | 테스트 코드 작성 및 수정 |
| `build` | 빌드 및 의존성 변경 |
| `rename` | 파일 및 폴더 이름 변경 |
| `delete` | 코드 및 파일 삭제 |
| `chore` | 환경 설정 및 기타 작업 |

### 작성 규칙

- Gitmoji는 사용하지 않는다.
- 타입은 영문 소문자, 작업 내용은 한글로 작성한다.
- 커밋은 하나의 논리적인 변경 단위로 작성한다.
- 내부 팀원은 Jira 티켓 번호를 반드시 포함한다.
- 외부 기여자는 한글 또는 영어로 작성할 수 있으며, Issue 번호는 선택 사항이다.

### Jira 티켓 번호 자동 삽입 (도입 예정)

Git Hook을 활용하여 브랜치의 Jira 티켓 번호를 커밋 메시지 첫 줄 끝에 자동으로 추가할 예정이다. 설치 전에는 티켓 번호를 직접 작성한다.

```bash
# 개발자가 입력
git commit -m "feat: 카카오 로그인 API 구현"

# 실제 저장되는 메시지
feat: 카카오 로그인 API 구현 (S15P31A108-123)
```

- `prepare-commit-msg` Hook을 사용한다.
- 중복 삽입을 방지한다.
- 브랜치에 Jira 티켓 번호가 없으면 자동 삽입하지 않는다.
- 팀원에게 공통 Hook 설치 방법을 제공한다.
- GitHub 웹 커밋에는 로컬 Hook이 적용되지 않으므로 티켓 번호를 직접 확인한다.

## 5. Pull Request 컨벤션

### PR 제목

커밋과 같은 소문자 타입을 사용하며, 대괄호 형식은 사용하지 않는다. 외부 기여자는 Jira 키 대신 GitHub Issue 번호를 사용하거나 번호를 생략할 수 있다.

`<type>: <설명> (지라 키)`

**내부 팀원**

```
feat: 카카오 로그인 API 구현 (S15P31A108-123)
fix: 로그인 토큰 만료 오류 수정 (S15P31A108-124)
```

**외부 기여자**

```
feat: 로그인 기능 개선 (#42)
docs: Update installation guide
```

### PR 템플릿

```markdown
## 개요
<!-- 이 PR이 어떤 작업을 하는지 한두 줄로 설명해주세요 -->

## 작업 내용
-
-

## 변경 사항
<!-- 주요 변경점, 영향 범위 등 -->

## 스크린샷 (선택)
<!-- UI 변경이 있다면 첨부해주세요 -->

## 관련 이슈
<!-- Jira 티켓 링크 또는 키 (예: S15P31A108-123) -->
<!-- 외부 기여자는 GitHub Issue 링크 또는 번호 (예: #42) -->
-

## 체크리스트
- [ ] 로컬에서 정상 동작 확인
- [ ] 테스트 코드 작성/통과
- [ ] 리뷰어 지정
```

### 코드 리뷰 규칙

- 일반 작업 PR은 `dev`를 대상으로 생성한다.
- 본인을 제외한 **쓰기 권한이 있는 리뷰어 최소 1명의 Approve**가 있어야 Merge할 수 있다.
- 리뷰어는 코드 변경, 기능 동작, 테스트 및 컨벤션을 확인한다.
- 수정 요청을 반영하고 리뷰 대화를 해결한 후 병합한다.
- 작업 중인 PR은 Draft 상태를 활용한다.

## 6. Merge 컨벤션

### 브랜치 운영

| 브랜치 | 용도 |
| --- | --- |
| `main` | 안정적인 배포 및 공개 버전 |
| `dev` | 개발 기능 통합 및 테스트 |
| 작업 브랜치 | 개별 기능 개발 및 수정 |

**기본 흐름**

`작업 브랜치 → dev → main`

### Merge 규칙

- `main`, `dev`에 직접 Push하지 않는다.
- 작업 브랜치 → `dev`: **Merge commit**
- `dev` → `main`: **Merge commit**
- Squash Merge는 저장소 설정에서 비활성화한다. Rebase merge도 비활성화한다(저장소 설정과 룰셋 모두). dev 배포 잡은 dev 본줄기의 PR 머지 커밋만 배포하는데, Rebase merge는 PR 커밋을 하나하나 본줄기에 올려 리뷰하지 않은 중간 커밋까지 배포 대상이 되게 만든다(`docs/infra/cd.md` "검사를 고정 파이프라인에 두는 이유"). 다시 켜려면 그 검사부터 바꾼다.
- 최소 1명의 Approve와 미해결 리뷰 대화 해결 등 브랜치 보호 조건을 충족한 후 병합한다.
- 필수 상태 검사로 지정된 CI가 있다면 모두 통과해야 한다. 빌드·테스트 CI는 현재 도입 예정이다.
- Merge 후 Jira 티켓 또는 GitHub Issue 상태를 확인한다.
- 긴급 수정으로 `main`을 변경한 경우 `dev`에도 반영한다.
- PR 템플릿 등 기본 브랜치 반영이 필요한 저장소 공통 설정은 목적을 PR에 명시하고 `main` 대상으로 생성할 수 있다.

### 승인 후 자동 병합

- 저장소의 Allow auto-merge를 활성화한다.
- `Enable PR auto-merge` Actions가 일반 PR의 Merge commit 자동 병합을 예약한다. 전용 Secret 등록과 워크플로의 dev 병합이 선행되어야 한다.
- 설정 전 또는 Actions 실패 시 PR 작성자가 Enable auto-merge를 선택해 수동 예약한다.
- 설정과 기존 PR 적용 방법은 [PR 자동 병합 가이드](pr-auto-merge.md)를 따른다.
- 승인 1명 및 나머지 보호 조건이 충족되면 GitHub가 자동 병합한다.
- 저장소 기능만 켜서는 자동 예약되지 않으며, 예약용 Actions가 성공했는지 확인한다.
- 자동 병합은 승인·미해결 대화·필수 검사 조건을 우회하지 않는다.
- 새 커밋으로 승인이 취소되면 다시 승인을 받아야 한다.
- 자동 병합 후에도 GitLab 동기화 성공 여부는 Actions에서 별도로 확인한다.

## 7. 외부 오픈소스 기여 컨벤션

### GitHub Issues

외부 기여자는 GitHub Issues를 통해 버그를 제보하거나 기능 개선을 제안한다.

| Issue 유형 | 설명 |
| --- | --- |
| Bug Report | 오류 및 재현 방법 |
| Feature Request | 신규 기능 및 개선 제안 |
| Documentation | 문서 오류 및 개선 |

**주요 라벨**

`bug`, `enhancement`, `documentation`, `good first issue`, `help wanted`, `question`

### 외부 기여 절차

1. 기존 Issue 확인 또는 신규 생성
2. 저장소 Fork 및 브랜치 생성
3. 코드 수정 및 테스트
4. 원본 저장소 `dev` 대상으로 PR 생성
5. 내부 팀원 코드 리뷰
6. 승인 후 Merge 및 Issue 종료

### 운영 규칙

- Jira 접근 권한과 티켓 번호를 요구하지 않는다.
- 한글 또는 영어 커밋과 PR을 허용한다.
- GitHub Issue 번호는 사용을 권장하되 강제하지 않는다.
- 외부 기여에도 동일한 코드 리뷰 기준을 적용한다.
- 별도 `CONTRIBUTING.md`가 준비되면 개발 환경과 상세 기여 절차를 연결한다.
- `Closes #42` 등의 자동 종료 키워드는 기본 브랜치 병합 기준으로 동작한다.
- `dev` 병합 후 Issue를 종료하려면 완료 기준을 확인하고 수동으로 종료한다.

## 8. GitHub · GitLab · Jira 연동

### GitHub → GitLab 자동 동기화

```text
GitHub Push
    ↓
GitHub Actions
    ↓
GitLab 자동 동기화
```

- GitHub를 기준으로 GitLab에 코드를 단방향 동기화한다.
- 브랜치, 커밋, 태그를 동기화 대상으로 한다.
- GitHub Issues, PR 및 리뷰 정보는 동기화하지 않는다.
- GitLab에 직접 Push하거나 MR을 병합하지 않는다.
- 동기화 실패 시 GitHub Actions 로그를 확인한다.
- 강제 덮어쓰기와 브랜치·태그 삭제는 자동 동기화하지 않는다.
- 동기화된 브랜치의 삭제 및 이력 충돌은 별도 관리한다.
- Git LFS 객체는 현재 워크플로의 전송 대상이 아니므로 도입 시 별도 전송 단계를 추가한다.
- 인증 토큰은 GitHub Actions Repository Secret `GITLAB_SYNC_TOKEN`으로 관리한다.
- 세부 운영 절차는 [GitLab 동기화 가이드](gitlab-sync.md)를 따른다.

### Jira 연동 및 자동화

| 자동화 | 동작 |
| --- | --- |
| 브랜치 생성 | 연결된 작업이 해야 할 일이면 진행 중으로 변경 |
| PR/MR 병합 | 연결된 작업이 완료가 아니면 완료로 변경 |
| 모든 Sub-task 완료 | 모든 하위 작업이 완료되면 상위 작업을 완료로 변경 |

**주의 사항**

- 위 표는 현재 저장한 규칙의 동작이며, 규칙 활성화와 실제 이벤트 실행 성공을 구분한다.
- 티켓의 인수 조건·테스트·배포 완료 여부는 자동으로 판단하지 않는다. 담당자가 확인한다.
- 추가 검증이 필요한 티켓은 병합만으로 완료되지 않도록 규칙 조건을 보완한 후 적용한다.
- Jira 자동화는 연결된 개발 도구에서 해당 이벤트를 수신해야 동작한다.
- GitHub → GitLab 코드 동기화는 GitLab MR 병합 이벤트를 생성하지 않는다.
- GitLab MR 자동화로 GitHub PR 병합을 감지할 수는 없다.
- 개발 도구 연동이 완료되지 않은 경우 Jira 상태를 수동으로 관리한다.
- GitHub–Jira 직접 연동 또는 별도 자동화 도입 후 실제 동작을 검증한다.

### 도입 및 검증 현황

최종 문서 갱신일: 2026-10-19. 외부 설정은 변경될 수 있으며, 아래 연동 상태는 마지막 확인 결과를 기준으로 한다.

| 항목 | 상태 |
| --- | --- |
| GitHub → GitLab 동기화 | main·dev Push에 따른 전송 및 커밋 일치 확인 완료 |
| GitHub 동기화 설정 PR #1 | main 병합 완료, dev 생성 및 동기화 확인 완료 |
| main·dev 브랜치 보호 | PR 필수, 승인 1명, 미해결 대화 해결, 새 커밋 시 기존 승인 취소 |
| 병합 방식 | Squash·Rebase 비활성화(Rebase는 2026-10-30 S15P31A108-123), Merge commit만 사용 |
| 승인 후 자동 병합 | 저장소 기능 활성화. 자동 예약용 Actions 추가, 전용 Secret 등록 및 dev 병합 필요 |
| PR 템플릿 | PR #3에 추가, main 병합 후 새 PR에 자동 표시 |
| Jira 자동화 규칙 3개 | 활성화 |
| GitLab–Jira 연동 | 관리자 검토 대기 |
| GitHub–Jira 직접 연동 | 미완료 |
