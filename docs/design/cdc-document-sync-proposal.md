# 문서·설계 변경 CDC 준비안

> 현재 합의: #197 접수행이 사후 영향 분석 상태의 유일한 기준이다. 최초 v1은 변경 제안 없이 `NOT_EVALUATED`, 197 이전 baseline은 197 migration이 `NOT_EVALUATED`로 백필한다. 변경 발행만 `PENDING`으로 접수한다. 최초 관계 구축은 #167, 색인은 #223의 기존 경로이며 CDC가 중복 실행하지 않는다. 아래 outbox·큐 계약과 검증은 합의 전 PoC 이력이다. #197 실제 스키마·수동 재분석·lease/fencing과 재처리 계약은 아직 연동되지 않았다.


> 논의용 초안. Kafka 도입·운영 방식과 각 서비스의 연결 계약은 팀 합의 전이다. 로컬 실험의 성공은 운영 도입이나 온톨로지 갱신 구현 완료를 뜻하지 않는다.

## 목적과 현재 흐름

승인된 설계가 바뀌었을 때 커밋된 변경을 감지하고, 최신 기준에 맞는 관계 재확인과 영향 분석 등 **후속 처리의 접수**를 신뢰성 있게 연결하는 방안을 준비한다. 승인 전 변경 제안 분석은 CDC를 기다리지 않고 별도로 수행한다.

현재 문서 업로드·새 버전 생성은 `document_processing` 작업을 만들고, 기존 `DocumentIndexWorker`가 청킹·임베딩·pgvector 저장을 처리한다. CDC로 이를 다시 실행하지 않는다. 승인, 권한, 기준 설계와 확정 관계의 원본은 PostgreSQL이다. 최초 발행과 관계 저장·재확인 표시는 원래 업무 트랜잭션의 책임이며, CDC 지연 때문에 승인이 달라져서는 안 된다.

## 목표 흐름 (제안)

```text
사람이 설계 변경을 승인·발행
    │
    ├─ BE: 기준·설계·관계 재확인 표시 등을 하나의 트랜잭션으로 저장
    └─ DB 커밋
          ↓
      PostgreSQL WAL → Debezium → Kafka
          ↓
      CDC 수신자: 프로젝트·발행 버전 식별, 중복 방지 및 작업 접수
          ↓
      원본 DB에서 승인된 스냅샷과 관계 상태 확인
          ↓
      별도 재분석·파생 결과 갱신 (담당 서비스와 계약 후 연결)
```

예: 인증 정책 `P v1`이 `P v2`로 발행되면 커밋 후 변경을 감지하고 `P`의 현재 승인 버전과 관계를 조회한다. `API A → P`, `작업 T → A`가 확정된 상태라면 담당 규칙 서비스가 T를 영향 **후보**로 찾아 별도 분석할 수 있다. 관계가 재확인 대기이거나 CDC 처리에 실패했다면 영향이 없다고 표시하지 않는다. 후보만으로 승인 관계·작업 상태를 자동 변경하지 않는다.

## 핵심 설계와 미결 사항

| 항목 | 준비 방향 | 확인 필요 |
| --- | --- | --- |
| 감지 범위 | 예제 테이블로 먼저 캡처를 검증한다. 실제 허용 테이블·컬럼은 발행 담당자와 정한다. | 발행 단위 식별자와 어떤 변경이 후속 작업을 유발하는지 |
| 트랜잭션 | 행 이벤트 하나를 곧바로 완성된 발행으로 해석하지 않는다. 여러 행이 함께 바뀌는 발행의 완료 경계를 정한다. | 전용 발행 이벤트/트랜잭션 메타데이터 중 채택 방식, 스냅샷 조회 시점 |
| 순서·중복 | 최소 한 번 전달과 재처리를 전제로 한다. 같은 발행의 중복을 안전하게 처리하는 저장 키·순서를 설계한다. | Kafka 키·파티션, 소비자 처리 완료 기록과 offset 커밋의 원자성 |
| 복구·초기 적재 | 스냅샷, 장애·재시작, WAL 보관, 소비 지연 및 누락 복구를 별도로 검증한다. | 초기 적재 범위, 정합성 검증, 재처리·DLQ·알림 기준 |
| 삭제·보안 | 삭제 이벤트와 비공개 데이터·접근 권한을 별도로 정의한다. | 허용 컬럼, 보존 기간, 로그 마스킹 및 권한 검증 위치 |
| 중복·루프 방지 | 인덱싱 및 CDC가 생성한 파생 데이터는 캡처 대상에서 제외하는 것을 기본 제안으로 둔다. | 실제 캡처 allowlist, 소비자 부작용과 반복 이벤트 방지 |
| 최신성 | 발행 버전, 관계 리비전, 처리 상태와 기준 시각을 파생 결과와 함께 확인한다. 지연·실패를 빈 결과와 구분한다. | watermark 의미와 재분석 허용 조건 |

`document_processing`, `document_chunk`, `document_index_manifest`는 기존 인덱싱 처리의 내부 테이블로, 이번 CDC 실험의 대상이 아니다. `baseline`, `baseline_item`, `design_item_dependency` 등도 실제로 캡처할 테이블을 확정한 것은 아니다. 특히 행 단위 이벤트만으로 동일 트랜잭션의 여러 변경이 모두 소비됐다는 보장은 없다.

## 단계

1. 격리된 로컬 PostgreSQL·Debezium·Kafka에서 커밋된 생성·수정·삭제 이벤트와 기본 재시작을 실험한다. 실제 프로젝트 DB와 연결하지 않는다.
2. 발행·관계·영향 분석 담당자와 발행 단위 이벤트, 처리 책임, 최신성 및 실패 정책을 합의한다. 기존 브로커 미사용 아키텍처 변경도 함께 결정한다.
3. 합의된 계약으로 소비자·중복 처리·복구 및 테스트를 구현하고 기존 문서 색인과 겹치지 않는지 검증한다.
4. 운영 도입이 승인되면 장애 복구, WAL·디스크·메모리, 보안, 모니터링과 기존 데이터 초기 적재를 검증한다.

관련 문서: [개발 맥락 그래프 검토](development-context-knowledge-graph-review-S15P31A108-110.md), [시스템 아키텍처](01-system-architecture.md). 로컬 실험 방법은 `infra/cdc-poc/README.md`를 참고한다.

## 결정한 범위와 임시 구현

- 사용자가 최초 기준과 이후 변경 **발행**을 동기화 대상으로 정했다. 초안과 파싱 상태만의 변경은 발행 동기화를 실행하지 않는다. 이 결정은 Jira의 문서 버전 캡처 검토와의 차이를 담당자와 맞춰야 한다.
- 사용자가 버전은 1부터 시작해 발행마다 1씩 증가한다고 확인했다. 최초 초기화 기준 이후 앞 버전이 누락되면 뒤 작업을 실행하지 않는다. 실제 후속 발행 구현·트랜잭션에서도 같은 규칙이 적용되는지 PR에서 담당자가 확인한다.
- 기존 기준을 별도 bootstrap으로 접수하고 실시간 발행을 같은 프로젝트·baseline·작업 종류 키로 중복 방지한다. bootstrap 후보 페이지는 전역 스냅샷이 아니고 CDC 커넥터 시작 전 발생한 간극을 해결하지 않는다. CDC checkpoint·재조정이 확정되지 않아 현재 안전한 초기 적재 완료로 표시할 수 없다.
- 후속 작업은 최초 시도와 최대 세 번 재시도(1·5·30초 대기), 최종 실패 보존을 목표로 한다. Kafka/DB 접수 자체의 연결 복구와는 별개다. 테스트용 큐 기능이며 실제 자동 실행 워커와 관계·AI·저장 연동은 없다.
- 늦게 도착한 과거 발행은 보존하고 프로젝트를 RECONCILE로 차단한다. 실행 시도가 없는 순서 뒤바뀜은 내부 복구 연산으로 되돌릴 수 있으며, 진행 중 lease는 대기하고 만료 lease나 이미 실행된 작업은 수동 재구축 대상으로 남긴다. 권한 있는 운영 API 및 수동 재구축 절차는 아직 없다.

## 과거 PoC 발행 이벤트 계약 (실제 #197 계약 아님)

최초 발행과 후속 발행은 `publication_kind`로 구분한다. 현재 dev에는 최초 발행이 있고 후속 발행은 #200의 작업이다. 최초 발행을 변경 영향 분석 요청으로 자동 취급하지 않는다. 이 계약은 #200·#167·#197·#180 담당자와 조율할 제안이다.

```json
{
  "event_id": "d2d11f91-c69f-48bf-9e36-c4656053065d",
  "event_type": "DESIGN_PUBLISHED",
  "event_version": 1,
  "publication_kind": "CHANGE",
  "occurred_at": "2026-10-29T06:00:00Z",
  "project_id": "10",
  "baseline_id": "8",
  "previous_baseline_id": "7",
  "change_proposal_id": "42",
  "changed_items": [
    {
      "design_item_id": "101",
      "previous_version_id": "201",
      "published_version_id": "202",
      "change_type": "UPDATED"
    }
  ]
}
```

`event_id`는 이벤트별 UUID다. DB ID는 bigint이며 이벤트 JSON에서는 문자열로 전달한다. `occurred_at`은 이벤트 기록 시각으로 커밋 시각·처리 완료 시각이 아니다. 최초 발행은 `INITIAL`, 이전 기준과 변경 제안은 null이다. `changed_items`의 신규·수정·제외 표현, 실제 이벤트 크기 및 발행 담당 서비스의 이벤트 구성 책임은 후속 발행 연동 전에 정한다. 생략한 항목을 변경 없음으로 해석해서는 안 된다. 문서·본문 자체는 이벤트에 넣지 않는다.

발행 서비스는 Outbox 행과 baseline을 **같은 DB 트랜잭션**에 기록한다. 동일 발행의 재요청은 이미 발행된 결과를 반환하고 신규 이벤트를 만들지 않는다. CDC 수신자 처리와 offset 커밋은 별개의 경계이므로 소비자 중복 방지, 실패 복구, 최신성 확인이 별도 필요하다. `INITIAL` 처리 정책, Kafka 키와 프로젝트 단위 순서, 스냅샷 경계는 미확정이다.

## 과거 PoC 구현과 검증 상태

- 최초 발행 경로의 Outbox 삽입과 롤백·재요청 검증을 추가했다. 현재 `INITIAL` 이벤트의 `changed_items`에는 최초 기준에 포함된 항목을 `ADDED`로 기록한다. 후속 발행 #200은 아직 연결하지 않았다.
- 수신기는 기본 비활성화다. `INITIAL`과 `CHANGE`를 모두 `PENDING`으로 기록하고 같은 트랜잭션에서 발행 처리 작업을 접수한다. `PENDING`은 형식 검사와 새 baseline의 프로젝트 FK만 확인한 **수신 상태**다. 이전 기준·제안·변경 항목과 실제 발행 내용을 대조해 최신성을 확인한 상태가 아니다. 관계 조회·영향 분석·결과 저장을 실행하는 워커는 없다.
- 현재 CHANGE 파서는 이전 baseline, 변경 제안과 한 건 이상의 변경 항목을 요구한다. 문서만 바뀐 발행이나 최초 기준과 다른 삭제 표현은 수신 실패로 남으며, #200과 허용 범위를 합의하기 전 이 제약을 확정으로 취급하지 않는다.
- 격리된 PostgreSQL → Debezium → Kafka → 실제 Spring Kafka 수신기 → DB inbox 실험에서 커밋 이벤트 접수와 롤백 이벤트 미접수를 확인했다. 원본 DB와 BE 테스트 DB는 별개로 생성하고 테스트 ID를 합성해 맞춘다. 실제 발행 API에서 단일 DB로 이어지는 검증과 broker 장애·오프셋 커밋 실패·재전달은 아직 확인하지 않았다.
- 수신 이벤트에 대한 읽기 전용 사전 검증기는 Outbox 원본과 이벤트, 프로젝트와 발행 제안, 이전·신규 baseline의 항목 버전 차이를 비교한다. 과거 baseline이면 STALE, 중간 발행이 있으면 UNVERIFIED로 반환한다. 결과는 해당 시점의 확인이며 실제 작업을 실행하기 전에 다시 확인해야 한다. 문서 변경과 관계 검증은 포함하지 않고 자동 워커·분석 호출도 없다. Outbox의 보관·삭제 정책이 미정이므로 원본이 없는 경우는 별도 확인이 필요하다.
- 로컬 실험은 `snapshot.mode=no_data`로 시작 전 이벤트를 읽지 않으며 운영 설정이 아니다. 초기 적재·오프셋 복구, 프로젝트별 순서와 재처리, 비정상 메시지로 인한 파티션 정지의 감지·복구는 운영 전 합의하고 검증한다.
- 구형 PoC 마이그레이션 V13~V15는 테스트 전용 repeatable fixture `db/cdc-poc/R__cdc_poc_fixture.sql`로 통합해 운영 Flyway와 버전 번호 충돌을 피한다. 실제 #197 마이그레이션은 별도로 번호와 계약을 확정한다.

## #225 기준 기존 작업과의 차이

기존 실험은 발행 Outbox만 캡처한다. [#225](https://ssafy.atlassian.net/browse/S15P31A108-225)는 문서 등록·새 버전 및 커밋된 수정도 포함하므로 캡처 범위가 더 넓다. 현재 기존 `document_processing` 워커는 문서 색인을 담당하며 CDC가 이를 중복 실행하지 않는다.

문서 최초 검토 제출은 같은 DRAFT 버전 행의 내용과 `lock_version`을 변경하고, 후속 제출은 새 버전을 생성할 수 있다. 반면 승인 상태·파싱 상태 변경은 다른 의미의 UPDATE다. 원본 CDC는 변경을 캡처할 뿐 이를 임의로 승인이나 내용 변경으로 판정하지 않는다. `document_version`의 프로젝트는 `document`와의 연계가 필요하며 권한과 식별 방식은 문서 담당자와 합의한다. 본문·저장 경로 등은 Kafka에 포함하지 않도록 캡처 대상을 제한하고 원본 DB의 복제 권한도 따로 검토한다.

초기 snapshot 이후 스트리밍과 경계 시점의 변경, 재시작·오프셋 복구, 문서 생성·수정·승인 및 롤백, 개인정보 비노출은 각각 실험과 실제 통합 결과를 구분해 확인한다. 설계 발행과 문서 초안 변경은 서로 다른 신호다.

### 격리된 문서 캡처 실험

`infra/cdc-poc/document-capture/`는 실제 프로젝트 DB가 아닌 별도 PostgreSQL 17·Debezium·Kafka로 문서와 버전의 허용된 메타데이터를 캡처한다. 커넥터 시작 전 생성된 행의 snapshot, 이후 생성·같은 버전 내용 수정·승인·파싱 상태 변경과 rollback, 커넥터 중단 중 커밋 후 동일 슬롯 재기동 복구를 확인했다. Kafka key·schema·value에서 테스트 원문·저장 경로·해시 등 제외 필드가 나가지 않는지도 검사했다. 단 원본과 일부 컬럼·흐름만 닮은 예시 데이터다.

기본 replica identity의 버전 삭제 이벤트는 실제 문서 ID를 보존하지 못하며 이 실험에서는 `before.document_id=0`이 관측됐다. 이를 실제 ID로 간주하지 않는다. 캡처된 `document_version`에는 프로젝트 ID가 없고, UPDATE가 어떤 업무 변화를 뜻하는지는 이 실험에서 분류하지 않는다. snapshot 진행 중 동시 쓰기, 다중 파티션 순서, 실제 서비스 및 consumer, 운영 보안은 검증하지 않았다. `infra/cdc/`의 설정은 검토용이며 운영에 자동 적용하지 않는다.


## #197 단일 접수 합의 및 남은 연동

오서현 담당자가 발행 트랜잭션에서 분석 접수행을 PENDING으로 생성하고 CDC가 이를 소비하는 안을 제안했다. 단일 접수 책임과 최초 발행·백필 정책은 합의됐으며 물리 테이블과 세부 컬럼은 아직 확정되지 않았다. 현재 브랜치의 `publication_outbox`, `cdc_publication_inbox`, `cdc_processing_job`은 이 제안 이전에 만든 실험 구현이며, #197 접수행과 별개로 두면 단일 접수 책임과 상태의 중복이 생긴다. 실제 연동 전 캡처 대상·접수/상태의 단일 진실 원천·멱등 키를 합의하고 구조를 조정한다.

남은 항목: 접수 테이블·컬럼 및 재분석 전환 계약, PENDING 스냅샷과 신규 INSERT 수신, 상태 UPDATE의 재처리 방지, RUNNING lease/만료·fencing, 재시도 횟수 및 FAILED/NOT_EVALUATED 의미, 프로젝트별 순서, 사전·사후 분석의 대상과 멱등 키. PENDING 장기 체류 재처리는 상태 변경 이벤트만으로 보장되지 않으므로 스캔과 중복 방지·원자적 claim이 필요하다.
