# CDC 발행 접수 Consumer 작업 기준 (#226)

## 범위와 책임

- #197은 발행 트랜잭션에서 분석 접수행을 생성하고 분석 상태·결과의 단일 기준을 소유한다. v1과 과거 백필은 `NOT_EVALUATED`, 변경 발행은 `PENDING`이다.
- #226은 접수 변경의 전달, 안전한 재수신·중복 방지·순서·복구를 담당한다. #227은 실제 분석 서비스 연결을 담당한다. 최초 관계 구축(#167)과 색인(#223)을 소비자가 다시 실행하지 않는다.
- Jira #226의 문서 초안·등록 변경 전달 보완 문구는 현재 사용자와 합의한 발행 기준 범위와 차이가 있다. 문서 캡처 여부는 담당자 합의 전 본 구현의 업무 처리 대상으로 확대하지 않는다.
- #225의 outbox/inbox와 별도 처리 큐는 PoC다. 운영에서 #197과 별개의 접수·상태 저장소로 연결하지 않는다.

## 수신 흐름

1. Debezium이 접수행 변경을 Kafka에 전달한다. 실제 테이블명, 컬럼, snapshot·UPDATE payload 및 삭제 정책은 #197 구현과 확인한 후 어댑터에서 정한다.
2. Consumer가 받은 이벤트는 작업 실행 명령이 아니라 현재 접수 상태를 확인하라는 신호다. INSERT·snapshot·UPDATE의 `PENDING`만 확인 대상으로 삼고 `NOT_EVALUATED` 등은 무시한다. 수동 재분석 시 상태 전환 규칙은 아직 확정하지 않는다. 실제 Kafka null tombstone은 무시하지만 접수행 DELETE는 보존·삭제 계약이 정해지기 전 오류로 남겨 건너뛰지 않는다.
3. Kafka offset을 진행하기 전 #197 어댑터는 현재 행을 확인하고 더 이상 처리 대상이 아니거나, 원자적 선점 이후 프로세스가 중단돼도 만료 lease의 재탐색·복구가 보장되거나, 대기 상태가 보장된 재탐색 대상인 등 이후 처리가 유실되지 않음을 보장해야 한다. 단순 선점만으로는 충분하지 않다. 단순히 PENDING을 읽기만 하고 돌아오는 것은 안전하지 않다. DB 확인·디코딩 오류는 전파해 해당 레코드를 건너뛰지 않는다.
4. 이벤트는 중복·지연·역순으로 올 수 있다. snapshot에 남은 PENDING이 나중에 COMPLETED가 된 뒤 재전달될 수도 있어 이벤트 상태만 신뢰하지 않는다. DB와 Kafka offset은 한 트랜잭션이 아니며 정확히 한 번 수신이나 LLM 실행을 가정하지 않는다. `auto.offset.reset=earliest`는 Kafka에 남아 있는 가장 이른 레코드부터 시작할 뿐 만료·삭제된 과거 레코드를 복구하지 못한다. 보관 만료 감지와 DB 대조·재탐색을 운영 계약에 포함한다.
5. #197의 attempt·lease·fencing 및 결과 저장이 확정되면 원자적 조건부 선점과 결과 기록을 연동한다. 이전 작업자의 오래된 결과는 새 시도 결과를 덮어쓰지 못해야 한다. 외부 LLM 호출은 fencing만으로 중복 호출이 방지되지 않는다.

## 순서와 재시도

- Kafka `project_id` 메시지 키는 동일 파티션 내 전달 순서를 돕지만 서로 다른 작업의 완료 순서를 보장하지 않는다. 파티션 수 변경에 따른 키 재배치와 비동기 완료를 고려해야 한다.
- 프로젝트별 순서·누락 판단, v1/백필 `NOT_EVALUATED`를 건너뛰는 기준은 실제 #197 접수·version 계약과 합의해야 한다. 순서 역전 감지 시 이미 수행한 외부 부작용을 자동으로 되감지 않는다.
- 업무 처리는 최초 1회와 최대 3회 재시도이며 실패 후 1·5·30초를 기다린다. 4번째 실패는 최종 실패로 남긴다. attempt, 다음 실행 시각 및 실패 상태는 영속 저장 및 재시작 시 재탐색이 필요하다. 이 정책은 Kafka 수신·DB 장애에 대한 전송 재시도와 별개다.

## 현재 검증 경계

이번 단계는 #197 물리 스키마에 의존하지 않는 전달 경계와 순수 정책을 준비한다. 실제 #197 테이블, 서비스, 운영 Kafka, 자동 분석이나 완료 상태 갱신이 연결됐다고 의미하지 않는다. 접수행 트랜잭션 구현 후 PostgreSQL·Debezium·Kafka를 결합해 신규/스냅샷/상태변경, DB 실패와 offset, 중복·역순, 재시작·stale lease, v1 및 백필 제외를 통합 검증한다.

## 구현된 연결점과 설정

- `beez.cdc.intake.enabled`는 기본적으로 꺼져 있다. 켤 때는 `beez.cdc.intake.bootstrap-servers`, `group-id`, `topic`과 #197 전용 decoder 및 durable intake-check adapter가 필요하다. 구현체가 빠지면 시작을 실패시킨다. 기존 `beez.cdc.legacy-outbox-poc-enabled`와 동시에 켤 수 없다.
- Kafka 자동 offset commit은 끄고 성공적으로 반환한 레코드만 처리한다. decoding·상태 확인 오류는 원문이나 DB 오류를 노출하지 않는 예외로 전파해 해당 레코드를 건너뛰지 않는다. 전송 오류는 별도의 무한 재시도이므로 잘못된 메시지는 파티션을 막을 수 있어 #243/#244에서 관측·알림·운영 대응이 필요하다.
- 보안 설정은 기존 `beez.cdc.kafka-security.properties`를 사용하며, 미설정 기본값은 로컬 PLAINTEXT다. 실제 운영 TLS/SASL 및 권한은 아직 검증하지 않았다.
- `ProcessingRetryPolicy`는 시각과 attempt를 계산할 뿐, 지연 예약·DB 영속화·실제 재시도를 실행하지 않는다. #197 adapter가 안전한 상태 전이와 복구를 보장해야 한다.
