# #110 개발 컨텍스트 MVP 조회·공유 경계 검토안

관련: [S15P31A108-110](https://ssafy.atlassian.net/browse/S15P31A108-110) · 다음 구현: [S15P31A108-131](https://ssafy.atlassian.net/browse/S15P31A108-131), [S15P31A108-132](https://ssafy.atlassian.net/browse/S15P31A108-132) · 상위: [S15P31A108-90](https://ssafy.atlassian.net/browse/S15P31A108-90) · 참고: [S15P31A108-95](https://ssafy.atlassian.net/browse/S15P31A108-95) · 작성: 박상은 · **제안안 v0.7, 담당자 검토 필요**

`get_development_context`(MCP-01) 첫 MVP 구현에 필요한 승인본·조회·공유 범위만 정리한다. #95의 개인 맥락·공유 확장 정책 전체를 선행 조건으로 두지 않는다. 개인 기록 수집·공유 확장은 구현하지 않는다. 기본 불변 패킷 저장은 TRC-03 MVP 범위이며 세부 구조는 4절에서 정한다.

MVP 제안안 (담당자 검토 필요)은 **정책 변경→API→작업의 규칙 기반 간접 영향 추론 한 시나리오를 MVP에서 검증**한다. 승인 전에는 현재 승인 기준과 변경 제안 초안을 분석하고, 승인 후에는 관계 재확인과 조회 모델의 최신성 확인 뒤 별도 재분석한다. CDC 도입 시에는 반영을 확인한다. 사전 결과는 검토 이력으로 보존하며 대기와 영향 0건을 구분한다. 상세 시나리오·데이터 구축·담당자별 합의는 [지식 그래프 재검토안](development-context-knowledge-graph-review-S15P31A108-110.md)의 3.5절을 따른다. 담당자 리뷰 중인 기준안이며 Jira나 기존 계약이 변경됐다는 뜻은 아니다.

CDC 작업은 양지훈님 담당으로 전달받았다. 도입 여부에 관한 기존 질문과 Debezium + Kafka를 포함한 도구·저장 방식·초기 적재·인프라/운영 담당 및 운영 보장은 별도 확인이 필요하며 기준 dev에서 구현은 확인되지 않았다. Kafka는 기존 브로커 미사용 방침과의 관계를 검토해야 한다. 담당자 의견은 [지식 그래프 재검토안](development-context-knowledge-graph-review-S15P31A108-110.md)의 3.6~3.7절에 출처별로 기록하며 계약 확정이나 다른 담당자의 동의로 간주하지 않는다.

라벨: **기존 계약** = 저장소 문서·DDL에 있음 · **구현됨** = dev 코드에 있음 · **제안** = 이 문서의 제안 · **합의 필요** = 담당자 계약 확인 전. 아래 기준과 담당자별 리뷰 의견을 구분하며, 기준안 자체가 구현이나 전체 계약 합의를 뜻하지 않는다.

## 먼저 볼 내용: MVP 기준과 남은 확인

아래는 동작 기준이며 아직 구현·연결되지 않은 부분을 포함한다. 실제 구현 범위는 1절에서 구분한다.

- **MCP-01:** 현재 승인 기준의 설계·원문 근거를 구분해 전달한다. 미연결·미준비는 `context_not_ready`로 실패하고, 실제 검색 후 근거 0건은 정상 응답의 `unresolved`로 구분한다 (B2·B4).
- **MCP-03:** D5 판정은 직접 참조만 사용한다. 변경 영향 후보는 확정 설계 관계 1단계와 작업 계획 참조로 계산한다. MVP 제안안은 `task_id` 유무와 무관하게 발행별 최대 10개를 반환하고, 전체 후보는 권한을 확인한 REST 페이지에서 조회하도록 한다. 발행·결과 변경 cursor를 분리하고 최초 진입은 지금부터 받는 방식으로 제안한다. 상세와 미완료 상태 노출은 [네 가지 제안](#analysis-watermark)을 따른다. 후보는 승인 설계나 자동 상태 변경의 근거가 아니다 (B5·B6·B10).
- **패킷 열람:** 현재 프로젝트 멤버는 REST와 기존 MCP-06 `PACKET`으로 자기 프로젝트의 패킷을 열람한다. 요청자의 `request`와 승인 설계도 공유 범위에 포함된다. 매 호출 현재 권한을 확인하며 별도 MCP 조회 도구는 추가하지 않는다 (3절).

## 2. 정보 출처와 권한 구분 (제안)

패킷은 지식 그래프의 조회 결과를 전달하는 표현이며, 저장된 불변 패킷은 실제 전달 내용의 실행 스냅샷이다. 지식 원본과 별도의 작업별 온톨로지를 만들지 않는다. 패킷의 각 필드는 출처와 권위를 섞어 표시하지 않는다 (POL-01). 원문 발췌는 저장하지 않고 승인 본문의 불변·보존과 정확한 위치가 보장될 때 재구성해 발췌 해시와 비교한다. 정확한 원문 범위와 결합 순서, 발췌·정규화 규칙과 인코딩도 버전으로 고정해야 하며, 재구성이나 해시 검증이 불가능하면 복원 불가·검증 실패로 표시한다. 표시용 행 범위만으로는 일부 분리·긴 행 청크를 재구성할 수 없다. 해시 자체가 전송 사실을 독립적으로 증명하지는 않는다.

| 구분 | 출처 (BE가 조회) | 패킷 필드 | 권위 | MVP |
| --- | --- | --- | --- | --- |
| 승인 설계 | `project.current_baseline_id`의 `baseline_item` → `design_item_version` | `design_items` | 팀장이 승인·발행한 기준 | 포함 |
| 의존 설계 | `design_item_dependency` 중 확정 조건을 확인했고 양 끝이 현재 기준에 있는 항목 | `design_items`에 함께 포함 | 항목의 승인과 관계의 확인은 별개. `EXPLICIT`만으로 확정을 보장하지 않음 | 포함, 1단계 (제안) |
| 변경 영향 후보 | #197의 규칙 영향 후보, `AI_CANDIDATE`, AI 추론 | MCP-03 `get_design_changes` 응답에 별도로 전달하는 제안 | 출처·방법·근거를 분리하는 후보. 후보만으로 관계 승인·게이트·무효화하지 않음 | 한 시나리오의 후보 전달. MCP-01 `impact_candidates`는 예약 또는 확장으로 미룸 |
| 승인 원문 근거 | `RetrievalScope.mode=APPROVED`의 `RetrievedEvidence` (현재 기준 문서 버전만) | `sources` | 승인 문서의 원문 위치. 그 자체가 설계 항목은 아님 | 포함 (4절 B4) |

세부 규칙 (제안):

- **두 입력 경로.** 설계 항목 자동 추출(#128)이 빠졌으므로 `design_items`가 비어 있을 수 있다. 이때도 승인 원문 근거로 관련 내용을 찾는다. 원문 근거만 있으면 "승인 문서의 원문 근거"로 표시하고, 승인된 설계 항목처럼 표시하지 않는다.
- 현재 기준의 `APPROVED`만 사용한다. 결과가 적다는 이유로 초안·과거 기준·`DOCUMENT_REVIEW`까지 넓히지 않는다 (05 문서 참고 2).
- 위 원칙은 MCP의 승인 설계 표현에 적용한다. 변경 제안의 **승인 전 영향 분석**에는 권한이 확인된 제안 초안을 검토 데이터로 전달할 수 있지만, 이를 승인 설계나 발행된 버전으로 표시하지 않는다.
- `unresolved`에는 승인 설계에 없거나 서로 충돌하는 내용, 근거가 부족한 부분을 넣는다. 검색 실패·색인 미준비를 "설계 없음"으로 단정하지 않고 별도로 표시한다 (POL-05, #131).
- `constraints`에는 출처가 있는 값만 넣는다. 승인된 `POLICY`·`CONSTRAINT` 항목을 어떤 문자열로 옮길지는 #132에서 정한다. AI 문장을 출처 없이 제약으로 넣지 않는다.
- 후보는 승인 설계나 자동 상태 변경의 근거가 아니다. 전진님 의견에 따라 후보 안내문은 MCP-01 `constraints`에서 제외하고 MCP-03 `impact_updates`의 후보 필드 설명과 도구 description에 "후보는 승인 설계가 아님"을 넣는다. `constraints`에는 출처 있는 승인 제약만 담는다. 전진님은 #39 머지 후 MCP-03 공용 계약을 반영할 예정이다.
- 다른 작업·기록 정보는 에이전트에게 **데이터**로 전달한다. 사용자 지시로 다루지 않는다 (00-common 2절).

## 3. `task_id` 처리 (제안)

MCP-01과 POL-07의 "`task_id` 없는 조회는 계획 수립용" 원칙을 따른다.

| 경우 | 동작 |
| --- | --- |
| `task_id` 없음 | 계획 수립용 조회다. 작업 생성·배정·점유·시작 허가로 취급하지 않는다. `related_tasks`는 같은 설계 항목을 참조하는 다른 작업만 담는다 |
| `task_id` 있음, 이 프로젝트 작업 | 그 작업의 현재 계획 리비전 참조(`design_refs`)를 관련 설계 선택에 반영한다 (#131 작업 내용 4). 작업 상태·계획·검증은 바꾸지 않는다 |
| `task_id`가 다른 프로젝트·없는 번호 | MCP-01 오류표대로 `not_found`. 목록 필터의 0건 규칙은 적용하지 않는다 |

- 다른 작업은 `RelatedTask`의 ID·리비전·상태만 담는다. 다른 사람의 계획 본문·기록 원문은 넣지 않는다. 겹침 판정은 검증(MCP-11)이 다시 한다.
- 시작은 기존 흐름대로 `upsert_task_plan` → `validate_task_plan` PASS → `report_task_state(START)`에서만 허가된다. 패킷 조회는 이 중 어느 단계도 대신하지 않는다.
- `task_id` 없이 만든 패킷도 이후 계획 리비전이 참조할 수 있다 (`ContextPacketLookup`이 이미 허용).
- 프로젝트 `MEMBER`면 담당자(`TASK_OWNER`)가 아니어도 같은 프로젝트의 `task_id`를 지정해 조회할 수 있다. #177 접근 제어에서 탐색 단계별 SQL 조건을 적용해 권한 없는 노드가 후보 경로·요약에 포함되지 않게 한다.
- **패킷 열람 기준 (10월 29일):** 변준성님의 제안에 전진님이 기존 REST 전용 의견을 정정했고, REST 대시보드와 기존 MCP-06 `read_context(PACKET)`을 MVP에서 유지하기로 결정했다. 현재 프로젝트 멤버가 자기 프로젝트 패킷을 열람하며 MCP는 매 호출 멤버십·토큰을 확인하고 탈퇴 멤버·폐기 토큰을 차단한다. 별도 MCP 패킷 조회 도구는 만들지 않는다. 패킷에 저장된 요청자의 `request`와 승인 설계 내용도 같은 프로젝트의 열람 범위에 포함된다. 다른 사람의 계획 본문·기록 원문이나 원문 발췌는 저장하지 않으며 그 밖의 자유 텍스트·민감 정보 처리 방식은 검토한다. #39의 MCP-06은 업무 서비스 구현이고 실제 MCP 경유 E2E는 별도다.

**자유 텍스트 기준안:** 전진님은 MVP에서 `request` 등 자유 텍스트를 마스킹하지 않고 MCP-01 도구 설명에 비밀번호·토큰 등 비밀값을 넣지 말라는 안내를 제안했다. `request`는 패킷에 저장되어 같은 프로젝트 멤버에게 공유되며, 안내만으로 비밀 입력이 차단되지는 않는다. 다른 자유 텍스트의 포함·공유 범위는 담당자 확인이 필요하다. MVP 제안안 (담당자 검토 필요)은 `request` 최대 2,000 Unicode 코드 포인트이며, 초과 입력은 `400 validation_failed`로 거부하고 잘라 저장하지 않는다. 전진님은 이 한도·오류에 동의했고, 변준성님은 한도 합의 시 Java 코드 포인트 기준으로 검증하겠다고 했다. 실제 구현과 공용 계약 반영은 후속 작업이다. 감사 기록에는 요청 본문을 남기지 않으며 애플리케이션 로그·예외·추적에서도 노출되지 않도록 확인한다.

**#197 분석 상태·전이 기준 (오서현님 의견, 담당자 확인 필요):** 변경 분석의 발행·단계(사전/사후)·실행 번호별 상태 행을 둔다. 사전 분석은 발행 전에 시작하므로 변경 제안·초안 리비전과 이후 발행을 연결하는 식별 방식은 별도 확정한다. 사전 결과와 사후 결과는 각각의 실행 이력이다. 다음 상태는 #197 제안이며 구현 완료를 뜻하지 않는다.

| 상태 | 의미 | 다음 전이 |
| --- | --- | --- |
| `PENDING` | 분석이 접수됐거나 입력·실행을 기다림 | 입력이 준비돼 실행할 때 `RUNNING` |
| `RUNNING` | 해당 실행이 분석 중 | 정상 결과는 `COMPLETED`, 실행 실패는 `FAILED` |
| `COMPLETED` | 해당 실행의 분석을 마침. 후보 0건은 이 상태와 후보 수 0으로 표시 | 재분석이 필요하면 새 실행을 접수 |
| `FAILED` | 해당 실행이 실패함. 후보 0건이나 정상 완료가 아님 | 재시도 시 실행 번호를 올려 새 `PENDING` 행 생성 |

오서현·변준성님은 사후 `PENDING` 행을 관계 저장·재확인 표시와 같은 발행 트랜잭션에 삽입하고 실제 분석 호출은 커밋 후 수행하는 안에 동의했다. 커밋 후 중단돼도 대기 행이 영구 방치되지 않도록 워커 재발견·복구와 중복 실행 방지 방식은 협의한다. 재시도·재분석에서 이전 상태 행은 보존한다. 결과를 현재 결과에 반영할 때 같은 대상·단계의 최신 실행 ID와 입력 해시가 모두 일치하는지 원자적으로 확인하며, 늦거나 불일치한 결과는 이력으로만 남기고 현재 결과에서 폐기한다. `COMPLETED` 자체는 최신성 보장이 아니다. 관계 집합 리비전이 `null`이면 최신성은 미확인이고 정의 후에도 기존 행을 소급해 채우지 않는다. 재분석이 필요할 때는 기존 이력을 바꾸지 않는 새 실행으로 처리한다. 접수 실패·워커 복구 등 실행 운영과 사전/사후 식별자는 담당자 협의가 필요하다. ### MCP-03 MVP 제안안 (담당자 검토 필요)

두 담당자의 후속 리뷰를 반영한 방향이다. 상세 필드와 상태 노출·조회 비용·일정은 담당자 확인 후 공용 명세에 반영한다. 리뷰 의견을 구현 완료나 전체 합의로 취급하지 않는다.

1. **실행 상태와 최신성:** #197 실행은 `PENDING → RUNNING → COMPLETED / FAILED`이며 `STALE`·최신성 미확인은 결과의 별도 평가다. 재분석 접수는 이전 실행을 보존한 새 `PENDING`이다. 미완료·실패·미확인·STALE은 최신이나 영향 0건이 아니다. 완료 결과만 변경 기록에 넣으면 장기 대기·실패나 이후 STALE을 알리지 못하므로, 상태·원인을 권한 내 MCP 응답 또는 대시보드에서 별도로 확인하는 경로를 제안한다. 제공 필드·알림·조회 주체는 전진·오서현님과 확정한다.

2. **발행·결과 두 cursor:** 전진님 후속안에 따라 `analyzed_through_version`은 제안 계약에서 제외한다. 발행 cursor는 발행 시점 `changed_items`·`affected_task_ids`를, 결과 cursor는 채택된 발행 후 첫 분석·재분석 결과의 `impact_updates[]`를 전달한다. 요청 `result_cursor`, 응답 `next_result_cursor`와 각 결과의 발행 ID·실행 ID·결과 순번·후보·잘린 수·최신성을 MCP-03에 추가하는 제안이다. 승인 전 분석 이력은 이 경로에 섞지 않는다. 중복은 결과 순번 또는 변경 기록 ID로 처리한다. `(발행 ID, 실행 ID)`는 채택된 결과 변경이 실행당 정확히 한 건일 때만 동등하다.

   오서현님은 결과 반영 시 실행 완료, 최신 실행 ID·입력 해시 조건부 현재 포인터 갱신, 실행별 후보 불변 저장 및 결과 변경 기록을 한 트랜잭션으로 제안했다. 후보 0건과 교체도 변경 기록을 만들고, 조건에 맞지 않는 늦은 결과는 이력으로만 남기며 새 변경 순번을 만들지 않는다. 기존·새 결과의 작업 ID 합집합을 작업 필터에 사용해 후보가 사라진 작업도 변경을 알 수 있도록 한다. 합집합은 내부 선택용이며 응답은 현재 권한을 확인해 권한 밖 ID·개수를 노출하지 않는다. [오서현님 상세 리뷰](https://github.com/S15A108/BEEZ/pull/40#issuecomment-6487945866)

   결과 순번은 별도 프로젝트별 카운터 행을 `FOR UPDATE`로 잠가 같은 결과 반영 트랜잭션에서 증가시키고 커밋까지 잠금을 유지하는 안이다. 번호 할당과 커밋 순서가 엇갈릴 수 있는 DB 시퀀스를 쓰지 않는다. 최초 카운터 행 생성 경합도 처리한다. 별도 카운터여도 공통 프로젝트·실행·현재 포인터 등의 잠금이 겹치면 대기·교착은 가능하므로 전역 잠금 순서와 재시도는 구현 담당자가 확인한다. 입력 해시에는 기준 ID·계획 리비전·관계 집합 리비전 등 실제 입력을 포함한다. 여러 읽기를 기본 `READ COMMITTED` 한 트랜잭션에 넣는 것만으로 같은 스냅샷은 보장되지 않으므로 단일 조회 또는 `REPEATABLE READ` 등으로 입력과 리비전을 일치시킨다. 분석 중 입력이 바뀌면 결과 반영·조회 시 최신성 판정 또는 변경 시 새 실행 접수가 필요하다. 외부 분석 호출은 읽기 트랜잭션 밖에서 수행한다.

   발행·결과 스트림 각각 첫 페이지에 조회 상한을 고정하고 페이지 위치·종료 여부를 유지한다. 응답의 `has_more=false`가 **양쪽 모두** 완료를 뜻하도록 계약하거나 스트림별 완료를 명시하고, 둘 다 순회한 뒤 두 cursor를 함께 확정한다. 페이지 중 새 결과는 고정 상한 이후 다음 조회에서 받는다. 현재 권한을 매 요청 확인하고 프로젝트·작업 필터나 권한 범위가 바뀌면 재조회 범위를 재설정한다. 삭제·보존 기간과 cursor 만료 시 명시적 재조회 방법은 담당자 확인이 필요하다. [전진님 리뷰](https://github.com/S15A108/BEEZ/pull/40#pullrequestreview-5692953509)

3. **후보 상한과 REST 전체 조회:** 후보는 실행별로 자르지 않고 보존한다. MCP 응답은 권한·`task_id` 필터와 중복 제거 후 발행 결과당 최대 10개이며 작업 필터에도 같은 상한이다. `candidates_truncated = max(0, 접근 가능한 필터·중복 제거 후 총수 - 10)`으로 권한 밖 수는 세지 않는다. 0보다 크면 전체 후보를 검토한 것으로 보고하지 말고 대시보드 확인을 안내한다. 전체 조회는 팀장 승인 화면과 공유하는 대시보드 REST 후보 API를 재사용하는 방향이며, 해당 API의 실제 구현·권한·과거 이력 범위는 확인 사항이다. 새 MCP 후보 도구는 추가하지 않는다.

   REST 페이지는 실행 ID와 정렬 키를 고정한다. 정렬은 진행 중 작업, API_CONTRACT·DATA_CONTRACT 우선, 작업 ID·후보 ID 순이다. 실행 ID만 고정해도 현재 작업 상태가 변하면 순서가 바뀔 수 있으므로 실행별 정렬 키 저장 또는 동등한 스냅샷을 제안한다. 매 페이지 현재 권한을 재검사하며 권한 변경 시 재시작 규칙을 둔다. 전체 저장과 권한별 count·인덱스 비용은 실측하고, 실행·변경 기록의 보존 기간과 오래된 cursor 처리 방식을 정한다. [오서현님 사례](https://github.com/S15A108/BEEZ/pull/40#issuecomment-6487953081)

4. **최초 진입은 지금부터:** MCP에 별도 이력 조회 모드는 두지 않는 전진님 제안을 따른다. 최초 `since_version=0`의 기존 최신 발행 1건 동작을 유지하며 응답에 현재 발행 번호와 결과 순번 상한을 다음 시작점으로 준다. 이때 이전에 완료된 간접 후보를 모두 읽은 것은 아니다. MCP-01은 현재 승인 설계를 주며 간접 후보를 대체하지 않으므로 기존 후보·이력은 대시보드에서 확인하도록 안내한다. 과거 미완료·실패 상태의 확인 경로와 실제 REST 이력 범위는 별도 합의 사항이다.

   최초 진입 표식과 정상 조회를 분리한다. 예를 들어 `result_cursor` 미제공은 초기화, 명시적 `result_cursor=0`은 결과 0 이후의 정상 구독이다. 발행 cursor도 정상 진행값이 0일 수 있으므로 초기화 표식으로 기존 최신 1건 특례와 구분한다. 0은 유효한 결과 순번 시작값이며 최초 변경은 1이다. 카운터는 프로젝트 생성 시 또는 첫 사용 시 경합 없이 생성하는 안을 담당자가 결정한다. 최초 발행 응답과 두 상한은 같은 스냅샷으로 읽거나 상한을 먼저 고정하고 중복을 허용해, 응답을 읽은 뒤 상한을 잡는 사이의 변경을 건너뛰지 않도록 한다. 초기 페이지를 끝까지 순회한 뒤 시작점을 확정하고 이후 변경을 다음 조회에서 받는 조건을 2번과 함께 검증한다.

**리뷰 맥락:** 기존 `PublishedChange.impact_candidates[]`와 직접 영향 OR 후보 OR 미완료 발행 선택 및 `analyzed_through_version`은 당시 리뷰안이다. 전진님의 후속 제안은 결과를 별도 `impact_updates[]`·결과 cursor로 전달하고 분석 완료 진행값을 제거하므로 현재 제안과 구분한다. 미완료 상태의 표시 의도는 유지하되 구체 경로는 아직 확정하지 않았다. 오서현님은 결과 저장·카운터·조회와 네 사례를 제안했고 전진님은 상태 분리·10개 상한에 동의했다. 두 호출 사이 과거 발행 재분석 완료, 페이지 중 결과 교체·작업 상태 변경, 최초 순번 0, 후보 11개, 후보 제거·0건, 분석 실패·장기 대기 및 권한 변경·cursor 만료를 검증한다. 구현·연동 검증 전에는 누락 방지나 전체 후보 전달이 완료됐다고 표시하지 않는다.

## 5. #131 구현 준비 (제안)

Jira #131 작업 내용을 AI 범위로 옮긴 계획이다. 저장·권한·기준 판정은 BE가 한다 (01 문서 원칙).

| Jira #131 작업 | AI 구현 범위 |
| --- | --- |
| 1. 요청에서 기능·도메인·키워드 추출 | 요청 문장을 검색 질의로 바꾼다. 원문 요청은 패킷의 `request`로 보존한다 |
| 2. 의미 검색으로 관련 승인 설계 조회 | 승인 항목 후보는 BE가 넘긴 목록 안에서 고른다. 원문 근거는 #129 질의 임베딩(`purpose=QUERY`)과 BE의 APPROVED 검색 결과를 쓴다 |
| 3. 명시 관계로 의존 설계 확장 | BE가 확정 조건을 확인해 넘긴 명시 관계를 1단계 확장한다. #167 API 전에는 fixture로 시험한다 |
| 4. `task_id` 있으면 작업·계획 반영 | 3절. 시작 허가·작업 생성 없음 |
| 5. 미확정 분류, 검색 실패 구분 | 2절. "근거 없음"과 "검색 실패·미준비"를 다른 상태로 반환한다 |
| 6. 대표 요청 예시 점검 | #130 가상 프로젝트 Markdown 4종으로 대표 요청을 만든다. 관련 없는 설계가 섞인 사례를 기록한다 |

- **입력** (BE가 권한·기준을 확인한 뒤 전달): `request`, 선택 `task_id`의 현재 계획 참조, 현재 기준 `DesignItemVersion[]` 후보, `EXPLICIT` 관계, APPROVED `RetrievedEvidence[]`.
- **변경 영향 후보 응답 제안**: 변경 이후 작업 담당 에이전트는 기존 규칙에 따른 `WAITING` 전환과 MCP-03 `get_design_changes`를 통해 변경을 확인한다. 간접 후보 자체가 `WAITING`을 유발하지는 않는다. #197 후보와 경로는 MCP-03에서 승인 설계와 구분해 전달하며 작업·계획·설계·관계 버전과 근거를 포함한다. MCP-01은 후보 필드를 예약하거나 확장으로 미룬다. 해당 응답 계약은 담당자 합의가 필요하다.
- **#188 연계 기준안·담당자 합의 필요**: AI가 규칙 후보를 설명하고 권한 검증된 승인 설계·작업 입력 안에서 추가 후보를 별도로 제시할 수 있다. 규칙 경로·문서 출처와 AI 해석을 구분한다. 규칙 후보·경로를 AI-A03에 넘기는 계약 및 확장 보류 범위는 별도 합의한다.
- **출력**: 입력 집합 안의 `design_item_version_id`·`evidence_id`와 선택 이유(`MATCHED`/`DEPENDENCY`/`TASK_PLAN`), 미확정 후보, 검색 상태. 입력 밖 ID, 승인 판정, 새 관계 확정은 반환하지 않는다.
- **실패**: 모델 실패나 #131·#132 구성 모듈 미연결을 빈 선택의 정상 성공으로 표시하지 않는다. 실제 검색을 완료했으나 근거가 없는 0건은 별도로 표현한다. 규칙만으로 가능한 처리(명시 의존 확장, 계획 참조 포함)는 모델 없이 먼저 한다.
- **검증**: 출력 ID 부분집합, 의존 깊이·순환, 빈 후보·빈 요청, 원문 근거만 있는 경우를 단위 테스트로 확인한다. 박상은이 규칙 시나리오의 입출력 명세·fixture와 계약 검증 사례도 준비한다. 유료 모델 호출 없이 fake provider로 시험한다.
- **브랜치**: Jira 지정 `feature/ai-context-retrieval-S15P31A108-131`. HTTP 경로·DTO와 B4 검색 연결을 정하고, 먼저 내부 함수와 fixture로 만든다.

**병렬 개발 방향:** MCP-01의 #131·#132와 패킷 서비스·#179 어댑터는 공통 계약과 fixture로 변경 영향 계산·#197·CDC·MCP-03 구현을 기다리지 않고 병행한다. 변경 영향은 관계 조회 → 규칙 계산 → #197 저장 → MCP-03 전달의 별도 경로로 개발한다. 승인 전 분석은 승인 후 CDC 반영을 기다리지 않는다. fixture 성공은 실제 통합 완료가 아니며, 실제 MCP-01 호출과 변경 영향 E2E는 각 경로의 실제 서비스·권한과 선행 기능이 준비된 뒤 검증한다.

## 7. 같이 고칠 문서 불일치 (발견)

- TRC-A01 응답 예시는 `relation: "DEPENDS_ON"`인데 `DesignDependency` 스키마는 `origin` 필드다.
- `ContextPacketLookup` 주석은 "패킷 엔티티는 S15P31A108-165에서 만든다"라고 적었지만, dev에 병합된 #165는 조회 이력만 다룬다.
- `dev_context_packet_ref`는 설계 항목의 프로젝트를 DB에서 강제하지 않는다 (`dev_context_packet`과 달리 복합 FK 없음). 저장 서비스에서 확인하거나 후속 migration이 필요하다.

담당 문서·코드라 이 문서에서는 고치지 않는다. 담당자 확인 후 반영한다.
