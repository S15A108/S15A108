# #110 개발 컨텍스트 지식 그래프 관점 재검토

관련: [S15P31A108-110](https://ssafy.atlassian.net/browse/S15P31A108-110) · [S15P31A108-95](https://ssafy.atlassian.net/browse/S15P31A108-95) · [S15P31A108-131](https://ssafy.atlassian.net/browse/S15P31A108-131) · [S15P31A108-132](https://ssafy.atlassian.net/browse/S15P31A108-132) · 작성: 박상은 · **제안안 v0.7, 담당자 검토 필요**

같이 볼 문서: [MVP 조회·공유 경계 검토안](development-context-mvp-boundary-S15P31A108-110.md)

프로젝트 개발 지식을 하나의 그래프로 연결하고 작업별로 탐색하며, 관계의 의미와 규칙을 이용해 간접 의존·변경 영향·충돌 후보를 추론하는 목표 구조를 기준으로 현재 설계를 대조한다. 기준은 GitHub dev `0af97f7`, ERD·V2~V5 migration, API·MCP 계약, Jira(2026-10-28 확인)다. **MVP 제안안 (담당자 검토 필요)은 MVP에서 규칙 추론 한 시나리오를 끝까지 검증한다. 담당자 리뷰 중인 기준안이며 Jira 범위·구현·팀 합의를 확정하지 않는다.**

이 문서의 구분:

- **확인된 사실**: 코드·DDL·문서·Jira에서 직접 확인한 내용. 1절과 2절의 상태 열.
- **MVP 제안안 (담당자 검토 필요)**: 이 문서의 MVP 기준 방향이다. 담당자들이 검토 중이며 확정된 Jira 요구사항이 아니다.
- **제안·합의 필요**: 기준안의 실현 방식과 타 담당 기능에 영향을 주는 세부 사항이다.
- **CDC 담당·검토**: CDC 작업은 양지훈님 담당으로 전달받았다. 도입 여부에 관한 변준성님의 기존 질문과 구체적인 최신성·운영 조건은 별도 확인하며 기술 선택이나 구현 완료를 뜻하지 않는다.
- **담당자 의견**: 양지훈·변준성·오서현·전진의 전달받은 의견이다. 명시적으로 확인된 계약과 구분하며 다른 담당자의 수용·Jira 범위 변경을 의미하지 않는다.

검토한 티켓의 관계·영향 분석 요구와 사용자 목표를 대조한다. 특정 용어의 사용 여부만으로 관련 기능의 요구 여부를 판단하지 않는다.

### MVP 제안안 (담당자 검토 필요)

`정책 ← API ← 작업` 한 시나리오에서 사람의 관계 확정·재확인과 규칙 후보를 검증한다 (3.5절). MCP-01은 승인 설계를, MCP-03은 영향 후보를 전달한다. 후보만으로 승인 설계·작업 상태나 기존 게이트·무효화를 바꾸지 않는다.

현재 기준과 담당자별 미결 사항은 [MVP 조회·공유 경계 검토안](development-context-mvp-boundary-S15P31A108-110.md)에서 먼저 확인한다. 이 문서에는 관계·이력·CDC·후보 전달의 근거와 상세 설계를 둔다. 기준안 자체로 Jira나 기존 계약이 변경되지는 않는다.

## 0. 결론

**부분적으로 지원한다.** 데이터 모델의 방향은 맞지만, 그래프를 채우고 따라가는 부분이 대부분 비어 있다.

- **지원하는 부분.** PostgreSQL 스키마가 이미 종류가 정해진 관계 표(설계 항목·버전, 기준 설계, 작업 계획 참조, 작업 의존, 검증 참조, 변경 제안, 공유 기록 참조)로 작업·설계·검증·변경·기록을 **버전 단위**로 연결한다. 승인된 것과 AI 후보를 나누는 표시(`EXPLICIT`/`AI_CANDIDATE`, `ExplicitImpact`/`ImpactCandidate`)도 계약에 있다. 그래프 DB 없이 목표 구조를 표현할 수 있는 기반이다.
- **지원하지 않는 부분.**
  1. 검토 기준 dev `0af97f7`에서 설계 항목·기준 설계·의존 관계의 운영 쓰기 경로를 확인하지 못했다. #128은 보류됐다. 오서현님이 수동 입력·발행의 #194 구현을 설명했으므로 최신 반영 상태를 확인한다. 관계 확정 경로는 후속 제안이다.
  2. 설계 사이의 관계(`design_item_dependency`)가 종류·버전·승인 이력 없이 현재 값만 가진다. 과거 시점의 관계를 복원할 수 없다.
  3. 관계를 따라가는 조회는 "바뀐 항목 → 그 이전 버전을 계획에서 직접 참조한 작업" 1단계만 구현됐다. 의존 관계를 거친 영향 탐색, 작업 중심 서브그래프 조회는 없다.
  4. 화면 설계 전용 항목 종류가 없다. 기존 문서·요구사항으로 표현 가능한 범위와 별도 유형의 필요성은 확인해야 한다.
- **바꿀 것 (제안).**
  - 패킷을 "지식 저장소"가 아니라 "그래프 조회 결과의 표현 + 실행 시점 불변 기록"으로 정의한다.
  - 기존 관계 표들을 하나의 개념 스키마(노드·관계 목록)로 문서화한다.
  - #167 관계 조회를 서브그래프 조회의 기반으로 삼는다.
  - 의존 관계의 의미·승인·이력 규칙을 합의한다.
  - 정책 변경 → API → 작업의 간접 영향 후보를 계산하고 근거와 함께 MCP에 제공하는 규칙 하나를 MVP에 제안한다 (3.5절).
  - CDC 도입 여부를 결정한다. 도입 시 승인 트랜잭션의 커밋된 변경을 지식 표현·추론에 반영하며 초기 적재·순서·재처리·일관성 등을 3.6절과 K12에서 결정한다.
  - 범용 edge 표나 그래프 DB는 MVP에 필요하지 않다.

## 2. 목표 구조와의 차이

### 2.1 노드

| 목표 노드 | 현재 표현 | 차이 |
| --- | --- | --- |
| 프로젝트 목표·요구사항 | 기획안 문서(PLAN), `design_item(kind=REQUIREMENT)` | 목표는 문서 원문으로만 존재 |
| 승인 설계 문서·항목 | `document_version`, `design_item_version`, `baseline` | 표는 있음, 생성 경로 없음 |
| API 명세·DB 스키마 | `API_CONTRACT`, `DATA_CONTRACT` 항목 + API_SPEC·ERD 문서 | 위와 같음 |
| 화면 설계 | 전용 UI·SCREEN kind 없음 (DOC-14 추가 첨부는 확장) | 기존 문서·요구사항으로 표현 가능한 범위와 전용 종류 필요성 확인 |
| 작업·계획 | `task`, `task_plan_revision` | 있음 |
| 담당 에이전트 | 담당 멤버·프로젝트 토큰·세션 | 실제 실행 에이전트의 식별·연결 기준은 별도 확인 필요 |
| 진행 상태·검증 | `task.status`, `validation` | 있음 |
| 공유 기록·의사결정 | `context_record` | 표는 있음. `DECISION`은 승인 설계가 아님 |
| 변경 이력·영향 | `change_proposal`, `approval`, `baseline` 연쇄 | 영향 결과 저장 표 없음 (#197) |

### 2.2 관계

| 목표 관계 (요청 예시) | 현재 표현 | 차이 |
| --- | --- | --- |
| 로그인 화면 작업 → 로그인 화면 설계 참조 | `task_plan_design_ref(READS)` | 화면 설계 전용 항목 종류가 없어 표현 방식 확인 필요 |
| 로그인 화면 작업 → 인증 API 의존 | `task_plan_design_ref(READS)` 직접 참조 | 계획이 직접 참조하면 표현 가능 |
| 인증 API → 인증 정책 참조 | `design_item_dependency` | 관계 종류가 없어 "참조"와 "의존"을 구분할 수 없음 |
| 인증 API → BE 인증 작업 | BE 작업의 `task_plan_design_ref(IMPLEMENTS)` | 있음 (역방향 조회) |
| BE 인증 작업 → 변경 기록 | `change_proposal.task_id`, `context_record.task_id` | 있음 |
| 인증 API 변경 → 영향받는 FE 작업 | `affected` SQL (직접 참조만) | 설계 의존을 거친 FE 작업은 찾지 못함 |

### 2.3 관계 메타데이터 (출처·승인·버전)

| 관계 | 출처 | 승인 여부 | 버전 |
| --- | --- | --- | --- |
| 작업 → 설계 | 작성 계정·토큰 (리비전) | 검증 PASS가 근거. 사람 승인은 없음 | 항목 버전 단위, 불변 |
| 설계 ↔ 설계 | `origin`, `confirmed_by/at` | `EXPLICIT`만으로 확정·승인을 보장하지 않음. 확인자·시각은 nullable이며 기준 발행·팀장 승인과 연결되지 않음 | **없음**. 항목 단위 현재 값. 변경 이력 없음 |
| 검증 → 설계 | 검증 실행 | — | 불변 스냅샷 |
| 변경 → 설계 | 제안자, `approval` | 팀장 승인 | 이전 버전 → 새 기준 |
| 공유 기록 → 설계 | 작성자 | 승인 아님 | 불변 |

가장 큰 공백은 **설계 ↔ 설계 관계가 승인·버전 체계 밖에 있다**는 점이다. 설계 항목 본문은 변경 제안 → 팀장 승인 → 기준 발행을 거치는데, 그 항목들 사이의 의존 관계는 같은 절차를 거치지 않는다. 그래서 "과거 AI가 참조한 의존 관계"는 검증 참조(`DEPENDENCY`)나 패킷에 스냅샷으로 남긴 경우에만 복원된다.

### 2.4 시나리오: 인증 API 응답 필드 변경

| 단계 | 계약·DDL | 구현 | 비고 |
| --- | --- | --- | --- |
| 1. BE 에이전트가 변경 제안 | MCP-04, `change_proposal(_item)` | 없음 (#195, MCP #179) | 제출만으로 설계·작업 상태가 바뀌지 않음 (MCP-04) |
| 2. 관련 설계·의존 확인 | CHG-A01 "명시 관계 영향 먼저", `design_item_dependency` | 없음 (#167, #197) | AI 영향은 별도 후보 (CHG-A05) |
| 3. 승인 시 새 설계 버전 | CHG-A09, 버전 불변 트리거, 기준 스냅샷 | 없음 (#198, #200) | 의존 관계는 새 기준에 포함되지 않음 |
| 4. 연결된 FE 작업 탐색 | `affected` | **직접 참조만 구현됨** (#164) | 의존을 거친 FE 작업은 빠짐 |

| 6. 후속 컨텍스트에 최신 승인 반영 | MCP-01 "현재 승인 설계" | 컨텍스트 없음. 현재 버전 해석은 구현됨 | 패킷은 새로 만들고, 과거 패킷은 그대로 둔다 |
| 7. 과거 참조 버전·실행 컨텍스트 추적 | 계획 참조·검증 참조·패킷 불변, 조회 이력 | 계획 참조·조회 이력 구현됨 | 의존 관계의 과거 상태는 스냅샷이 없으면 복원 불가 |

AI 추정 관계 구분은 계약상 지켜진다. D5는 "AI 추론 관계는 무효화에서 제외", AI-A03은 "AI 결과는 자동 승인·작업 수정 근거가 아님", DesignDependency는 "AI 후보는 무효화 근거가 아님"으로 정해 두었다.

## 3. 아키텍처 제안 (제안)

### 3.1 기존 표를 그래프로 정의한다

새 저장소나 범용 edge 표를 만들지 않는다. 기존 표를 **종류가 정해진 관계형 그래프**로 보고, 노드·관계 목록과 각각의 권위 수준을 개념 스키마로 문서화한다.

| 권위 수준 | 해당 노드·관계 | 컨텍스트에서의 취급 |
| --- | --- | --- |
| A. 승인 기준 | 현재 기준의 설계 항목 버전·문서 버전 | 개발 판단의 근거 |
| B. 명시 관계 | `EXPLICIT` 의존, 계획 참조(READS·IMPLEMENTS·CHANGES), 작업 의존 | 권한·확정 조건을 검증한 탐색 경로. `EXPLICIT` 값만으로 승인 관계라 단정하지 않음 |
| C. 작업 상태 | 작업 상태·검증 상태·변경 제안 상태 | 현재 상황 정보. 설계가 아님 |
| D. 공유 기록 | `SHARED` 기록 | 동료가 남긴 데이터. 승인 설계가 아님 |
| E. 추론·AI 후보 | 규칙 영향 후보, `AI_CANDIDATE`, AI 영향 후보 | 출처·방법을 구분해 후보로 표시. 후보만으로 공식 설계·작업 상태나 무효화를 변경하지 않음 |
| 제외 | 타인의 `PRIVATE`, 다른 프로젝트, 미승인 초안 | 조회 결과에 노출하지 않음 (요약·건수 포함). 권한이 있는 과거 버전은 변경 근거·스냅샷에서 과거로 명시 |

### 3.2 네 가지 개념의 분리

| 개념 | 정의 | 저장 위치 | 현재 대응 |
| --- | --- | --- | --- |
| 지식 그래프 저장 | 위 표들. 계속 관리되는 원본 | 기존 표 | 일부 구현 |
| 컨텍스트 조회 | 작업을 기점으로 서브그래프를 탐색하는 BE 조회 서비스 | 저장 안 함 | 없음. #167이 기반 |
| 컨텍스트 패킷 | 조회 결과를 AI에게 주는 구조화 표현 (MCP-01 응답) | 응답 | #132 |
| 실행 스냅샷 | 실제 제공한 내용과 참조 버전의 불변 기록 | `dev_context_packet(_ref)` | DDL만 있음 |

`dev_context_packet`은 TRC-03 MVP의 기본 패킷 보존용으로 설계돼 있으며 DDL과 UPDATE 금지 트리거가 있다. #90에서 제외한 것은 확장 패킷이다. 기존 표는 실행 스냅샷이다. 기준 dev에는 생성 구현이 없었고 #166 PR #39의 작업 브랜치 구현은 1.2절과 구분한다. 다음 저장 방식은 기준안이며 세부 계약은 담당자 합의 전이다.

- 호출마다 새 패킷 행을 만들고 재사용하지 않는다. `ContextAccessRecorder`는 `MANDATORY`이므로 패킷 저장과 조회 이력 기록을 같은 트랜잭션에 묶는다. 00-common의 담당 분담에 따라 도구는 전진, 업무 저장은 변준성이 맡고 #179 어댑터는 입출력 변환만 한다.
- 원문 발췌는 저장하지 않고 `content`에 `evidence_id`, `document_version_id`, `locator`, 발췌 `text_hash`를 기록하는 계약 변경을 제안한다. **위치:** `locator`에는 원문 조각의 정확한 `source_spans`와 결합 순서를 담고, 정규화·인코딩·스키마/해시 버전을 고정한다. 기존 청크의 행 범위 `locator`는 표시용이므로 분리 span·긴 행에선 정확한 발췌 복원에 충분하지 않다 ([AI 내부 계약](../api/03-ai-internal.md)). 이 `text_hash`는 실제 전달 발췌 해시로 정의하며 `ValidationEvidence.text_hash`의 전체 정규화 원문 해시와 혼동하지 않도록 스키마별 의미를 구분한다. 별도 필드명·버전과 span 표현은 담당자 계약 합의 사항이다. 선택·요약 등 발췌가 아닌 실제 전달값은 별도로 보존한다. 승인 본문의 불변·보존과 정확한 범위 및 규칙이 보장되어야 재구성할 수 있다. 전제가 충족되지 않거나 해시가 다르면 복원 불가·검증 실패로 표시한다.
- `content_hash`는 실제 전달 payload 기준의 정규 직렬화·해시로 계산하는 안이다. 실제 전송 바이트와 규칙, 참조의 유지·접근 가능성을 #132·#166 담당자가 합의한다. #39 `1473ea0`의 코드와 서비스 계약은 저장한 `{project_id, task_id, request, baseline_id, content}`의 정규 JSON 해시를 명시한다. 이는 전송 payload 전체 해시와 원문 발췌의 `source_spans`·발췌 해시 계약이 완성됐다는 뜻이 아니다. 이 문단은 후속 계약 제안이다.

현재 DDL은 패킷 부모 행의 UPDATE만 차단한다. `dev_context_packet_ref`의 변경·삭제 방지와 프로젝트 정합은 별도 보강이 필요하다. 패킷 보존은 전달한 패킷의 추적이며 에이전트가 별도로 구성한 전체 프롬프트나 모델 응답까지 자동 재현한다는 뜻은 아니다.

### 3.3 작업 중심 서브그래프 조회 (BE 서비스)

`task_id`가 있을 때 (현재 계획 리비전 기점, 깊이 1 제안):

1. 현재 계획의 `task_plan_design_ref` → 참조 항목 버전. 현재 기준 버전과 비교해 최신 여부 표시 (구현된 `ProjectDesignLookup`·시작 게이트와 같은 규칙)
2. 그 항목의 명시 의존 1단계 (확정 조건을 확인하고 양 끝이 현재 기준에 있을 때만. `EXPLICIT` 값만으로 확정하지 않음)
3. 같은 항목을 참조하는 다른 작업의 ID·리비전·상태
4. 그 항목에 걸린 진행 중 변경 제안 (상태만)
5. 선택: 이 작업·항목을 참조하는 `SHARED` 기록 요약 (MCP-05~07 범위 결정 후, 기본 제외)

`task_id`가 없을 때는 연결된 관계가 없으므로 검색이 기점이다. 승인 설계 항목 매칭 + APPROVED 원문 검색으로 후보를 찾고, 그 후보에서 2~4를 확장한다. 이 결과는 **관계로 저장하지 않는다**. 계획 등록(`upsert_task_plan`)에서 에이전트가 참조를 명시해야 비로소 작업→설계 관계가 생긴다. 시작 허가·작업 생성은 기존 검증 절차만 한다.

`task_id` 지정은 해당 프로젝트 `MEMBER`면 충분하다. #177 접근 제어는 그래프 탐색 단계마다 SQL 조건을 적용해 권한 없는 노드가 후보 경로에 끼지 않도록 한다 (프로젝트, 현재 기준, `SHARED OR 작성자 본인`). 탐색 후 필터로 대체하지 않는다 (05 문서 합의 5번).

| 관계 | 생성 주체·시점 | 상태 |
| --- | --- | --- |
| 작업 → 설계 | 계획 등록·수정 때 에이전트·사람이 명시 | 구현됨 |

### 3.5 MVP 규칙 추론 시나리오 (담당자 검토 필요)

**기준안:** 수동으로 확인한 관계를 바탕으로 정책 변경의 간접 영향 후보를 계산하고, 근거를 저장해 MCP 컨텍스트에 전달한다. 이 규칙 하나가 실제로 동작하는 것을 MVP에서 검증한다. 범용 추론 엔진이나 #128 자동 추출을 선행하지 않는다.

#### 관계 구축과 변경

1. 사람이 PLN-A07 수동 입력 경로로 인증 정책 `P v1`과 로그인 API `A v1`을 등록한다. 문서 버전·원문 위치를 기록할 수 있다. 오서현님은 #194 수동 등록·수정·제외 및 발행 구현을 설명했다. 검토 기준 dev `0af97f7`에서는 확인되지 않아 최신 반영 상태를 따로 확인한다.
2. 기존 PLN-A10 최초 기준 설계 발행 요건에 따라 항목과 문서를 승인하고 기준 `B1`을 발행한다. 필수 문서·분석 상태·검토 해시 등 기존 검증을 생략하지 않는다.
3. 최초 발행 전에는 관계를 초안으로 함께 검토하고 팀장이 `A DEPENDS_ON P`를 확정한다는 담당자 제안이다. 관계 리비전·근거와 검토 스냅샷·리비전 해시에 관계를 포함하는 방식은 합의한다. 관계 입력은 #194 병합 후 후속으로 제안됐으며, `EXPLICIT` 값 자체는 승인 증거가 아니다.
4. FE 작업 `T`의 현재 계획 리비전이 `A v1`을 `READS` 또는 `IMPLEMENTS`로 참조한다. 작업 계획 참조는 기존 저장 기능을 사용한다.
5. 변경 제안을 제출하면 팀장 **승인 전**에 현재 승인 기준 `B1`의 `P v1`과 변경 제안 초안을 비교해 규칙·AI 영향 후보를 분석한다. 초안은 승인된 `P v2`가 아니며 검토 대상으로만 전달한다. 제안 리비전·내용 해시, `B1`·관계·작업 계획 리비전과 규칙/모델 버전을 분석 스냅샷으로 남긴다. 입력이 바뀌면 사전 결과를 최신으로 취급하지 않는다.
6. 팀장 승인·발행 트랜잭션에서 `P v2`, 기준 `B2`, 관계 저장·이력과 재확인 필요 표시를 처리한다는 두 담당자의 리뷰 의견이다. CDC 도입 여부와 무관하며 서비스 입력·반환·실패 계약은 합의가 필요하다. 커밋 후 최신 상태와 사람의 관계 재확인을 거쳐 **별도 승인 후 분석**을 수행한다. CDC 도입 시 동기화와 최신성도 확인한다. 승인 전 결과는 당시 검토 이력으로 보존하되 승인 후 결과로 자동 재사용하지 않는다. `P v1`·제안 초안·실제 `P v2`와 각 분석 실행의 관계를 추적한다.
7. 변경에 연결된 기존 관계를 자동 해제하지 않고 **재확인 필요**로 표시한 뒤 팀장이 유지·해제한다. **MVP 제안안 (담당자 검토 필요):** 재확인 전에는 이 관계를 승인 후 규칙의 확정 근거로 사용하지 않고 해당 범위의 분석을 대기한다. CDC 지연·관계 재확인 대기·분석 실패는 영향 0건이 아니다. 재확인 필요 표시는 CDC와 무관하게 발행 트랜잭션에서 처리한다는 변준성님의 의견이다. 사람의 유지·해제와 재분석 접수 경로는 별도 합의가 필요하다.

PLN-A07·PLN-A10의 수동 항목 경로는 #194 담당자 구현 보고와 기준 dev의 확인 결과를 구분한다. 관계 입력은 #194 범위 밖의 후속 제안이고 변경 제안의 관계 연산도 계약 반영이 제안됐다. fixture·SQL seed는 실제 등록→승인→조회 경로를 대체하지 않는다.

#### 규칙과 결과

**`POLICY_API_TASK_IMPACT` v1 — MVP 제안안 (담당자 검토 필요):** 변경 전 승인 정책 `P`와 변경 대상의 분석 스냅샷, 확정된 `API A DEPENDS_ON P` 및 작업 계획 `T READS/IMPLEMENTS A`가 같은 프로젝트에서 유효하면 `T`의 **간접 변경 영향 후보**를 만든다. 승인 전 변경 대상은 제안 초안, 승인 후 변경 대상은 실제 발행 버전이다. 승인 전에는 현 승인 기준의 관계를 사용하고, 승인 후에는 새 기준과 재확인이 끝난 관계를 사용한다. CDC 도입 시에는 동기화된 결과의 최신성을 확인한다. 관계 의미와 방향은 `A → P`, `T → A`이며 변경에서의 역방향 탐색 경로는 `P ← A ← T`다. 임의 관계의 전이성을 일반화하지 않는다.

**MVP 기준:** 후보에 확정된 설계 관계 1단계와 작업 계획 참조를 사용하고, 2단계 탐색은 도그푸딩 후 확장을 논의한다. MVP 제안안은 `task_id` 유무와 무관하게 발행당 후보 10개와 REST 전체 후보 페이지를 둔다. 세부 기준은 [경계 문서의 네 가지 제안](development-context-mvp-boundary-S15P31A108-110.md#analysis-watermark)을 따른다. 판정은 기존 D5대로 직접 참조만 사용한다. 전진님은 이전 깊이 제안을 철회하고 변준성님의 안에 동의했다. 박상은은 규칙 시나리오·입출력 명세·fixture·계약 검증을 준비한다. 변준성님은 관계 조회 API와 함께 BE 규칙 후보 계산을 맡고 결과를 #197에 넘기겠다고 답했다. 별도 Jira 작업을 생성하고 일정은 그 작업에서 정할 예정이다. 오서현님은 #197이 관계 서비스에서 계산 결과를 제공받는 구조로 이해했다.

결과의 `검토 필요`는 **추론 후보 상태**이며 validation의 `NEEDS_REVIEW`나 task의 `WAITING`이 아니다. 규칙·AI 후보만으로 공식 관계를 승인하거나 기존 직접 참조 기반 `STALE`, `WAITING`, 시작 게이트를 변경하지 않는다. AI-A02 후보는 별도 기존 검증 계약에 따라 BE의 검사·판정에 활용될 수 있다.

#### 최소 이력과 컨텍스트

| 저장 대상 | 최소 기록 (제안) |
| --- | --- |
| 확정 관계 리비전 | 프로젝트, 관계 방향·종류, 항목과 유효 버전/기준, 근거, 확인자·시각 |
| 추론 실행 | 승인 전/후 구분, 변경 제안 리비전·내용 해시, 이전 기준·승인 전 정책 버전, 발행 후 기준·실제 버전(발행 후에만), 관계·계획 리비전, 규칙/모델 버전, 실행 상태·시각 |
| 영향 후보 | 대상 작업·계획 리비전, 종류, 검토 상태, 실행 식별자 |
| 후보 근거 | API 버전, 관계 리비전·방향, 작업 계획 참조, 각 경로. 중복 작업은 묶되 경로는 보존 |
| 검토·전달 | 후보 검토 이력과 실제 전달한 후보·경로·규칙·버전의 보존 방식을 합의. 기본 패킷의 원문은 3.2절의 참조·발췌 해시로 보존 |

이는 논리 모델 제안이며 테이블·DTO를 확정한 것은 아니다. 전진님은 관계 원본의 `origin=EXPLICIT/AI_CANDIDATE`를 유지하고 **응답 후보 출처만** `candidate_origin=RULE/AI_CANDIDATE`로 분리할 것을 제안했다. 오서현님은 #197의 영향 분석 결과에 규칙 후보·경로를 저장할 수 있다고 설명했다. 이는 규칙 후보를 확정 관계로 저장한다는 뜻이 아니며, 별도 후보 저장 구조의 마이그레이션 필요 여부는 설계에 달렸다. 관계 리비전·당시 확정/재확인 상태 없이는 항목 버전 ID만으로 과거 관계를 복원할 수 없다. 발행 당시 이력·스냅샷이 없으면 분석 시점 관계라고 명시한다.

승인 전 분석은 제안 검토를 지원하고, 승인 후 분석은 발행된 지식의 최신 상태를 반영한다. 사전 결과는 불변 이력으로 보존하며 MVP에서는 승인 후 별도 재분석한다. 향후 재사용을 검토할 경우 제안 내용과 실제 발행 버전의 대응, 기준·관계·계획·규칙/모델 버전 및 권한과 (CDC 도입 시) 동기화 최신성을 모두 검증해야 한다. 사전 기준과 발행 후 기준 ID가 다르다는 사실만으로 내용이 달라졌다고 단정하지 않는다. 분석 접수·재시도와 유실·중복 방지는 BE 합의 사항이며, 결과가 늦게 도착해 최신 상태를 덮어쓰지 않도록 한다. 실패·권한 부족·재확인 대기를 **영향 없음**으로 표시하지 않는다. 조회·추론 입력부터 프로젝트·승인·공유 권한을 적용하며, #177에서 탐색 단계별 SQL 조건으로 권한 없는 노드가 후보 경로에 포함되지 않게 한다. 요약으로도 노출하지 않는다.

AI-A02는 계획 충돌 finding 후보, AI-A03은 의미적 변경 영향 후보를 담당하는 계약 초안이다. **MVP 제안안 (담당자 검토 필요):** 규칙이 후보·연결 경로를 찾고 #188 AI가 변경 내용·관련 문서를 비교해 영향 가능성을 설명한다. AI는 BE가 권한을 검증해 전달한 관련 승인 설계·작업 범위 안에서 규칙이 놓친 추가 영향도 **별도 AI 후보**로 제시할 수 있다. 승인 전에는 제안 초안을 미승인 검토 데이터로 구분한다. 관계 경로·문서 출처와 AI 해석을 분리하고, 근거 부족은 확인 필요로 남기며 AI 실패 시 규칙 후보를 보존한다. AI 후보만으로 승인·무효화·작업 상태를 변경하지 않는다. 규칙 후보와 경로를 AI-A03 입력으로 넘기려면 계약 변경이 필요하며 추가 후보의 MVP 범위와 확장 보류 합의를 양지훈님·오서현님과 확인한다.

### 3.6 CDC 도입 여부와 조건부 설계

**담당:** CDC 작업은 양지훈님 담당으로 전달받았다. 도입 여부는 변준성님이 질문한 사항으로 별도 확인한다. 양지훈님은 **Debezium + Kafka**를 기술 방향으로 제안했다. 구체 구성·별도 저장소·인프라/운영 담당은 확정되지 않았으며 검토 기준 코드에서 구현은 확인하지 못했다. 오서현님의 발행·#197 분석, 변준성님의 관계 서비스, 전진님의 MCP 접근 제어·응답과 CDC의 인터페이스 및 책임 경계는 각 담당자와 합의한다.

```text
승인 전: 승인 기준 + 변경 제안 초안 + 관계·계획 스냅샷
    → 규칙·AI 영향 후보 분석 → 승인 전 검토 이력 보존
승인 후: 사람의 승인 및 설계 발행 + 관계 저장·이력·재확인 필요 표시 (원본 DB 트랜잭션)
    → 최신 상태 반영·사람의 관계 유지/해제 확인 (CDC 도입 시 커밋된 변경 감지·동기화)
    → 규칙·AI 후보 별도 재분석 → #197 결과 보존
    → 권한을 검사해 MCP-03 후보·근거 전달
```

승인 설계와 권한 판정은 항상 PostgreSQL 원본에서 읽는다. CDC 도입 시 변경을 전달하며 관계 의미 추출, 팀장 승인, 기존 게이트·무효화 결정을 대신하지 않는다. 지식 표현은 기존 테이블을 이용한 조회 모델이나 별도 파생 모델 중 합의하며 별도 그래프 DB를 전제하지 않는다. 오서현·변준성님은 발행과 관계 저장·이력·재확인 필요 표시를 같은 PostgreSQL 트랜잭션에서 처리하는 방향을 확인했다. 기준안은 발행 트랜잭션의 어느 단계든 실패하면 전체 롤백한다. 승인 후 CDC·AI 등 외부 처리는 발행 커밋 이후에 수행하고, 승인 전 AI 분석은 발행 트랜잭션 밖에서 별도로 수행한다. 재확인 표시는 CDC와 무관하며 기존 직접 참조 기반 D5 무효화를 바꾸지 않는다. 관계 서비스 입력·반환·실패, 커밋 후 접수·재시도·중복 방지 계약은 미결이다.

CDC 초기 데이터 적재와 시작 지점의 일관성, 트랜잭션 단위 원자성·프로젝트별 순서, 중복·멱등성·checkpoint·재처리, 삭제·스키마 변경, 장애 복구·재구축·지연 모니터링, 권한·민감 데이터 최소화, 이벤트와 분석 실행의 연결은 **모두 미결**이다. 후보·감사 기록 등 CDC 산출물이 다시 원본 갱신으로 반복되지 않도록 캡처 범위·쓰기 소유권도 정해야 한다. 파생 모델이 뒤처지거나 기준·관계 버전이 불일치할 때 이를 영향 0건으로 반환하지 않고 대기·오류·미평가를 표시한다. Kafka 채택 시 기존 [브로커 없음 방침](01-system-architecture.md)과 충돌하므로 변경 합의가 필요하다. 구성·인프라/운영 담당 및 이벤트 유실 방지 Q03과의 관계를 확인한다. 도입 여부와 별개로 Debezium·Kafka 채택, 실시간 전달이나 정확히 한 번 처리를 가정하지 않는다.

전진님은 CDC 도입 여부와 무관하게 저장 후보에 `computed_baseline_id`, 계산에 사용한 `plan_revision_id`, 관계 리비전을 기록하고 현재 값과 비교하자고 했다. 변준성님이 정의한 **관계 집합 리비전**은 프로젝트별 확정 설계 항목 간 관계에 한정하며, 관계 초안·AI 후보·작업 계획 참조는 제외한다. 관계 저장 서비스만 프로젝트별 번호를 올리고 관계 이력에 해당 리비전을 기록한다. 확정 관계의 추가·변경·해제, 재확인 필요 표시 및 유지·해제 결과를 같은 트랜잭션에서 반영하며 발행에서 여러 관계가 바뀌어도 한 번만 증가한다. 프로젝트 행 잠금으로 동시 갱신을 직렬화한다. 관계 표가 생긴 뒤 확정 관계가 없는 프로젝트의 `0`은 알려진 값이고, 그 이전에 저장된 `null`은 모르는 값이다. 후보 리비전이나 현재 값을 알 수 없으면 최신성 미확인, 둘 다 있으면 일치 시 해당 관계 집합 기준 일치·불일치 시 `STALE`이다. 전체 최신성에는 baseline·계획도 따로 비교한다. 기존 `null` 행은 소급하지 않으며 재분석 시 새 실행을 만든다. 미확인·STALE은 최신이나 영향 0건이 아니다. 후보 상태와 이력은 [경계 문서](development-context-mvp-boundary-S15P31A108-110.md#impact-analysis-state)를 따른다. CDC 미동기·관계 재확인 대기도 구분한다. 리비전 비교만으로 동기화나 재계산 완료를 보장하지 않는다. [변준성님 리뷰](https://github.com/S15A108/BEEZ/pull/40#pullrequestreview-5692675700)

**발행 후 분석 상태:** 오서현님은 `PENDING → RUNNING → COMPLETED / FAILED`와 실행 번호별 상태 행, 최신 실행 ID·입력 해시 검사를 제시했다. 변준성님은 사후 `PENDING`을 관계 저장·재확인 표시와 같은 발행 트랜잭션에 넣고 분석 호출은 커밋 후 수행하는 안에 동의했다. 실제 구현과 워커 복구·사전 분석 식별은 [경계 문서의 #197 상태 기준](development-context-mvp-boundary-S15P31A108-110.md#impact-analysis-state)을 따른다.

**MCP-03 전달:** 변경 이후 `P ← A ← T`의 #197 결과를 MCP-03으로 전달한다. 기존 직접 영향 작업은 별도로 WAITING이 될 수 있지만 간접 후보 자체는 WAITING을 유발하지 않는다. MCP-01의 1단계 명시 의존은 `design_items`에 포함되므로 MCP-01의 `impact_candidates`는 예약 또는 확장으로 미뤄 중복 제공을 피한다. MCP-03의 `impact_updates`와 결과 cursor는 기존 공용 계약에 없는 후속 제안이며 전진님이 명세 반영을 맡는다.

**MCP-03 후보 응답 기준안 (계약 변경 제안):** #197 결과의 대상 `task_id`·계획 리비전, 후보 출처(`candidate_origin`), 항목 버전과 관계 리비전을 잇는 방향·근거 경로, 사유, 분석 시점·상태 및 기준 ID를 포함한다. 규칙 후보는 규칙 ID·버전을 포함하며 AI 후보의 규칙 필드는 선택이다. 관계 원본의 `origin`과 후보 출처는 구분한다. 분석 실행 상태와 결과 최신성(`STALE`·미확인)을 분리하며, 대기·실패·미평가·STALE을 정상 분석의 후보 0건으로 표시하지 않고, 권한 없는 노드는 경로나 요약에도 넣지 않는다. 후보만으로 D5 판정·무효화나 `WAITING`을 바꾸지 않는다. 기존 MCP-03 `items`·`has_more`·`next_cursor`와 후보의 필터·정렬·페이지 범위는 담당자 합의 후 계약에 반영한다. 규칙 집합 버전을 코드 상수로 두는 안과 출처별 필수 필드는 별도 확인한다.

전진님이 처음 제안한 `PublishedChange.impact_candidates[]`와 변준성님이 동의한 발행 선택 OR 조건은 [전진님 기존 리뷰](https://github.com/S15A108/BEEZ/pull/40#pullrequestreview-5691598824)와 [변준성님 리뷰](https://github.com/S15A108/BEEZ/pull/40#pullrequestreview-5692675700)에 보존한다. 후속 제안은 발행 시점의 직접 영향과 첫 분석·재분석 결과를 별도 cursor로 분리한다. 전진님은 MCP-03 공용 명세를 맡고 변준성님은 #197 저장 이후 조회를 구현할 예정이다. 변경된 계약의 구현 영향은 필요한 범위에서 확인한다.

**MVP 제안안 (담당자 검토 필요) — 전달·재조회:** 상세·담당자별 확인 사항은 [경계 문서](development-context-mvp-boundary-S15P31A108-110.md#analysis-watermark)를 따른다.

1. 실행 상태와 결과 최신성을 분리한다. 미완료·실패·STALE·미확인을 후보 0건으로 보지 않으며, 상태 노출 경로는 추가 확인한다.
2. 발행 cursor는 변경 항목·직접 영향을, `result_cursor`와 `impact_updates[]`는 첫 분석·재분석 결과를 전달한다. `analyzed_through_version`은 후속 제안에서 제외한다. 결과 저장·변경 기록은 같은 트랜잭션에서 처리하고 프로젝트별 카운터 잠금으로 결과 순번을 부여한다.
3. 권한·작업 필터와 중복 제거 후 결과당 후보 10개이며 `task_id` 조회에도 상한을 적용한다. 전체 후보는 승인 화면과 공유하는 대시보드 REST 페이지로 제안한다. 실행 ID와 정렬 키를 고정하고 현재 권한은 매 페이지 확인한다.
4. 최초 진입은 현재 발행 번호·결과 순번을 기준으로 지금부터 받는다. 과거 간접 후보는 MCP-01에서 대체하지 않으므로 대시보드 확인을 안내하며, MCP 별도 이력 조회 모드는 두지 않는다. 초기화 표식과 유효한 순번 0은 구분한다.

오서현님은 후보 0건·교체·늦은 결과, 이전·새 작업 ID 합집합과 후보 불변 저장 및 카운터 잠금 방식을 제안했다. 전진님은 결과 cursor와 대시보드 API 재사용·최초 진입 범위 축소를 제안했다. 현재 문서는 두 의견을 반영한 제안이며 공용 계약 변경·구현 완료는 아니다. [오서현님 저장 리뷰](https://github.com/S15A108/BEEZ/pull/40#issuecomment-6487945866) · [네 사례](https://github.com/S15A108/BEEZ/pull/40#issuecomment-6487953081) · [전진님 이전 의견](https://github.com/S15A108/BEEZ/pull/40#pullrequestreview-5692680944) · [전진님 후속 리뷰](https://github.com/S15A108/BEEZ/pull/40#pullrequestreview-5692953509)

전진님은 후보를 `task_plan_design_ref`에 넣지 않고 계획 `unlinked`에 확인 필요 내용으로 기재하고, 팀장 승인된 변경 제안으로 확정 관계에 반영하는 방향도 제안했다. 후보는 승인 설계나 자동 상태 변경의 근거가 아니다. MCP-01 `constraints`에는 후보 안내를 넣지 않고 MCP-03 `impact_updates` 후보 필드 설명과 도구 description에 "후보는 승인 설계가 아님"을 넣는다. 판정과 후보 깊이는 3.5절에 둔다.

**패킷 조회·감사:** REST·MCP-06 열람 범위와 #177 실패 감사의 분리·기록·접근 권한은 [경계 검토안 3~4절](development-context-mvp-boundary-S15P31A108-110.md#3-task_id-처리-제안)을 따른다. 원문 발췌 복원과 해시는 3.2절을 따른다. 검증 재사용 해시의 규칙 버전 적용 범위와 후보 조회 구조·H1 지표는 미결이다.

MVP에서 "이미 관계로 연결된 지식"이 실제로 존재하려면 **설계 항목이 입력돼야** 한다. #128이 빠진 지금은 설계 항목이 비어 있을 수 있고, 그러면 컨텍스트는 관계가 없는 원문 청크 검색에 의존한다. 원문 청크는 문서 버전에만 연결돼 있고 설계 항목·작업과 관계가 없다. 이것이 목표 구조와 MVP 사이의 가장 큰 현실적 차이다 (K3).

## 8. 구현 순서 (제안)

**담당자별 역할:** 박상은은 #131·#132와 규칙 시나리오·입출력 명세·fixture·계약 검증을 준비한다. 변준성님은 관계 기반 BE 규칙 계산을 맡고 별도 Jira 작업을 생성해 일정을 정할 예정이다. 오서현은 발행과 #197 저장·조회, 양지훈은 CDC와 #188 AI, 전진은 MCP·권한을 맡는다. 박민용의 변경 영향 FE 노출은 오서현과 화면/API 범위를 합의한 경우에 연결한다. 담당자 확인과 Jira 작업 생성은 구현 완료를 뜻하지 않는다.

2026-10-28 확인 당시 #131·#132 기한은 11-09였다. 선행 작업과 추가 제안의 담당·일정을 재확인해야 한다. fixture 개발을 병행하더라도 실제 서비스 경로의 E2E 완료로 대체하지 않는다.

**완료 조건 제안:** 승인 전에는 제안 초안에 대한 후보·근거·입력 스냅샷을 기록하고, 승인 후에는 최신 상태 반영·관계 재확인 후 별도 재분석한다 (CDC 도입 시 동기화 확인). MCP-01은 승인 설계를, MCP-03은 변경 영향 후보를 전달한다. 패킷은 원문 발췌를 참조·해시로 보존한다. 제안 수정·발행 내용 차이, 사전 이력 유지·사후 결과 연결, AI 추가 후보의 입력·근거 검증, CDC 도입 시 초기 적재·이벤트 중복/순서·복구/지연, 관계 미확정·권한 실패·분석 실패와 영향 없음의 구분, 후보에 의한 자동 상태 변경 금지를 검증한다.

## 9. 기존 MVP 경계 검토안과의 정합성

경계 검토안에도 패킷 정의, B0·B5·B6·B8과 3.5절 연계를 제안으로 반영했다. 아래 사항의 세부 문구·범위와 실제 계약이나 Jira 변경은 별도 합의가 필요하다.

1. 2절 표 앞에 "패킷 = 서브그래프 조회 결과의 표현, 저장 시 실행 스냅샷"이라는 정의를 넣는다 (이 문서 3.2).
2. B0에서 MCP-01·TRC-03의 기본 스냅샷 계약과 #90의 확장 제외 범위를 구분한다.
3. 2절 출처 표에 "권위 수준" 열을 이 문서 3.1의 A~E로 맞춘다.
4. 5절 #131 입력을 "BE가 조회한 작업 중심 서브그래프 + 검색 결과"로 다시 쓰고, 탐색과 선택의 담당 구분을 명시한다.
5. 4절 합의 항목에 K2(설계 의존 규칙), K4(영향 범위), K5(검증 의존 참조)를 추가하거나 이 문서를 링크한다.
6. 3.5절의 한 가지 규칙·후보 전달은 **MVP 제안안 (담당자 검토 필요)**으로 표시하고 담당자 합의 전 현재 #131·#132 요구로 단정하지 않는다.
