# #226 Consumer와 #197 발행 후 분석 접수 연동 계약 제안

이 문서는 오서현 님과 검토할 **제안**이다. #197 테이블·컬럼·상태 전이의 확정 명세나 실행 가능한 SQL이 아니다. #197 접수행이 사후 분석 상태의 단일 기준이며 #226은 별도의 접수행 또는 분석 결과 테이블을 만들지 않는다.

## 대상과 식별

- 발행 트랜잭션에서 접수행을 만든다. `(project_id, published_baseline_id)`는 유일하며 접수행 자체의 불변 식별자가 필요하다. 이벤트를 반복 수신해도 이 행으로 현재 상태를 조회한다.
- 최초 v1은 변경 제안 ID 없이 `NOT_EVALUATED`, #197 도입 이전 발행도 백필 `NOT_EVALUATED`다. 이후 변경 발행은 `PENDING`으로 접수한다. 최초 관계 구축(#167), 문서 색인(#223)은 별도 경로다.
- 프로젝트 및 baseline ID, 기준 버전 번호와 변경 제안 ID는 접수행에서 직접 받거나 같은 DB의 기준 설계에서 신뢰성 있게 조회한다. 전달 이벤트에는 식별과 처리에 필요한 최소 정보만 포함하고 문서 원문·민감정보를 포함하지 않는다.
- 의도적으로 영향 분석을 건너뛴 v1·과거 백필과, 근거 부족·오류·아직 확인되지 않은 `NOT_EVALUATED`는 동일하게 취급하지 않는다. 구분할 수 있는 **사유 정보와 값**을 함께 합의한다. 사유 없거나 확인이 불가능하면 선행 버전을 통과한 것으로 간주하지 않는다.

## 선점·순서·복구에 필요한 동작

1. **현재 상태 재확인:** Kafka의 `PENDING`은 힌트다. `c`·snapshot·`u`가 재전달되거나 오래됐을 수 있으므로 접수행의 현재 상태를 확인한다. 이미 처리 대상이 아니면 분석을 다시 실행하지 않는다. DELETE/보존·수동 재분석 전이는 별도 합의한다.
2. **같은 프로젝트의 순서:** 후보의 버전과 이전 버전 접수행을 같은 기준에서 확인한다. 선행 작업이 완료됐거나 합의된 의도적 미평가인 경우를 제외하면 대기한다. 조회 범위가 빠졌거나 다른 프로젝트의 행을 섞으면 안전하게 보류한다. Kafka 파티션 순서는 실제 처리 완료 순서가 아니다.
3. **원자적 선점:** 상태 확인·이전 버전 검사와 실행 권한 획득 사이의 경합을 막도록 DB 락 또는 동등한 원자적 조건부 갱신을 설계한다. 여러 consumer 인스턴스가 같은 프로젝트에서 경합해도 두 작업이 동시에 선점돼 뒤 버전이 먼저 완료되지 않아야 한다. 이름이나 SQL 형태는 #197 담당자와 정한다.
4. **lease/fencing:** 선점 시 현재 시도와 구별되는 fencing 값, lease 만료 시각을 보존한다. 완료·실패/재예약·결과 저장은 **현재 fencing 값과 유효한 상태**를 같은 트랜잭션에서 조건부 검사한다. 만료·교체된 작업자의 결과는 저장하거나 현재 상태를 덮어쓰지 못해야 한다.
5. **장애 재탐색:** 오래된 `PENDING`, 재시각이 도래한 대기 작업, lease가 만료된 `RUNNING`을 누락 없이 제한된 배치로 다시 찾는 방법을 제공한다. Kafka 메시지 확인 후 접수행을 선점했더라도 서버가 즉시 죽을 수 있으므로, lease 만료 후 내구적 복구가 보장되어야 offset을 안전하게 진행할 수 있다.
6. **업무 재시도:** 재시도 가능한 장애는 최초 실행 후 1초·5초·30초 간격으로 최대 3회 추가 실행한다. 네 번째 실패는 최종 실패로 남긴다. 시도·다음 실행 가능 시각·실패 상태는 재시작 후 복원 가능하게 영속화한다. 전송 장애 재시도와 별도다. 수동 재시도·영구 실패·근거 부족의 상태 전이는 #197 담당자와 확정한다.
7. **결과 경계:** #227은 분석 실행을 연결하고 #197은 결과를 저장한다. DB 저장과 Kafka offset 커밋은 원자적이지 않으므로 재전달을 정상으로 처리한다. 외부 LLM 호출은 중복될 수 있으며 fencing만으로 외부 호출의 정확히 한 번 실행을 보장하지 않는다.

## 담당자와 확인할 항목

- 최초 v1·과거 백필을 식별하는 미평가 사유 및 수동 재분석 전이.
- 접수행 ID·버전 조회·보관/삭제·CDC 이벤트 컬럼과 snapshot/stream 경계.
- 프로젝트별 순서 검사·선점·fencing과 결과 저장을 어느 서비스의 어떤 트랜잭션에서 보장할지.
- 작업 취소/연장·lease 만료·DB 장애·재전달·수동 복구 및 실패 코드 계약.
- 진단 지표와 운영 알림은 #243/#244에서 분리하고, 장애 통합 검증은 #229와 연계한다.

위 계약은 아직 실제 #197 DB나 #227 분석 실행과 연결·검증되지 않았다.
