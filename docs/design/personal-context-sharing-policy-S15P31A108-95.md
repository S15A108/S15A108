# #95 개인 맥락·공유 정책 검토안

작성: 박상은 · **정책 검토 및 합의 문서** · 기준: dev `9f9af95`, Jira 조회 2026-10-30

이 문서는 [#95](https://ssafy.atlassian.net/browse/S15P31A108-95)에서 정한 정책 방향과 팀 합의가 필요한 쟁점을 구분한다. 방향을 정했다고 해서 다른 담당자의 API·서비스 계약이나 개인 맥락 기능의 구현을 확정하는 것은 아니다. **기존 계약은 변경이 합의되고 해당 계약에 반영되기 전까지 유지한다.**

**읽는 순서:** 1절에서 기존 기준을, 2절에서 #95의 정책 방향을, 3절에서 구현과의 차이를 확인한다. 팀 합의와 구현 계약 확인이 필요한 항목은 4절에, 검증 초안은 5절에 정리했다.

상태 표기: **기존 계약**은 현재 명세·설계의 규칙, **구현 확인**은 기준 dev 코드에서 확인한 동작, **#95 정책 결정**은 이 검토에서 정한 방향, **팀 합의 필요**는 기존 권한·보안이나 구현 계약에 영향을 주는 미결 사항이다. 확인 대상은 의견을 요청할 사람이며 동의하거나 요청을 받은 사실을 뜻하지 않는다.

## 1. 검토 배경 및 기존 기준

### 목적과 범위

POL-01\~03·14의 컨텍스트 우선순위, 조회 수준, 개인 기록, 효과 실험을 검토한다. CTX-07\~09·11·12는 업무 분담안에서 개인 맥락으로 표시돼 있으나 요구사항 원문을 확인하지 못했다. 검토 당시 별도로 조회한 요구사항 정리본에는 CTX-01\~04만 있었고, POL 항목도 팀 미확정 검토안이다. **#95가 검토 작업이라는 사실만으로 해당 CTX 요구사항의 MVP 제외를 확정할 수 없다.**

선행 자료는 [#110 MVP 경계 검토안](development-context-mvp-boundary-S15P31A108-110.md), [지식 그래프 재검토안](development-context-knowledge-graph-review-S15P31A108-110.md), [MCP 도구 명세](../api/02-mcp-tools.md), [공통 접근 정책](05-build-order-and-access-policy.md)이다. #110의 패킷 범위와 감사 방식은 담당자 확인이 필요한 **제안**이다.

### 기존 계약과 기준 dev 구현

- **기존 계약:** 타인의 PRIVATE 기록은 상세 조회 시 404이며 검색 결과와 건수에도 포함하지 않는다. 프로젝트 권한은 매 호출 확인한다 ([접근 정책](06-project-access.md), MCP-05·06).
- **기존 계약·구현 확인:** 기록 수정은 기존 리비전을 참조해 새 리비전을 만들며 같은 이전 판의 동시 수정은 `409 revision_conflict`다. `DECISION` 기록은 승인 설계가 아니다. ERD의 공통 규칙은 물리 삭제 없음이며 `context_record` UPDATE는 트리거가 차단한다.
- **구현 확인:** `ContextRecordService`에 `write_context`·`read_context(RECORD)`·`find_context` 업무 로직이 있고 MCP 업무 서비스가 이를 호출한다. REST CTX-A02\~A04의 실제 연결과 MCP 전송 경유 호출은 별도 확인이 필요하다. `visibility`는 필수지만 사용자의 명시적 확인을 서버가 검증하지 않는다. 검색은 `summary` 문자열 포함과 작업·종류 필터를 사용하고, 보이는 모든 리비전을 반환한다.
- **구현 확인:** `context_record.embedding` 열은 있으나 기록 임베딩을 채우는 경로는 확인되지 않았다. 비밀값 형식 검사와 이 문서에서 제안하는 길이 상한도 확인되지 않았다. 이는 MCP 전송 경유 통합이나 새 정책이 구현됐다는 뜻이 아니다.
- **선행 제안:** #110은 공유·개인 기록을 MCP-01 패킷에서 제외하고 MCP-01 감사에서 `request` 본문을 남기지 않는 방향이다. 아직 기존 확정 계약으로 취급하지 않는다.

이번 PR은 #95의 정책 방향을 정하고, 기존 혼합 체인의 PRIVATE 존재 노출·탈퇴 기록의 최종 처리·CTX 원문처럼 확인이나 합의가 필요한 쟁점과 개발 과정에서 담당자가 검토할 노출 사고 대응을 구분한다.

## 2. 정책 결정과 합의가 필요한 쟁점

각 절에서 **#95 정책 결정**으로 표시한 내용은 이 검토에서 정한 방향이다. 구체적인 적용과 남은 쟁점은 개발 전 확인, 개발 과정의 담당자 결정 또는 **팀 합의 필요**로 구분한다.

### 2.1 근거 우선순위와 충돌 (C1·C2)

**#95 정책 결정:** [지식 그래프 검토안](development-context-knowledge-graph-review-S15P31A108-110.md)의 분류를 따라 **승인 기준 → 명시 관계 → 작업 상태 → 공유 기록 → 추론·AI 후보** 순으로 구분한다. 관계는 탐색 경로이고, `DECISION`을 포함한 공유 기록과 AI 후보는 승인 설계가 아니다. AI는 승인 설계를 임의로 변경하거나 하위 근거로 덮어쓰지 않으며 출처와 버전을 유지한다.

**#95 정책 결정:** 공유 기록과 승인 설계의 충돌은 패킷과 별도로 기록을 조회한 소비자가 승인 설계를 기준으로 두 출처를 구분하고 검토 필요를 표시한다. 변경이 필요하면 MCP-04 `propose_design_change`를 이용한다.

공유 기록을 MCP-01 패킷에서 제외하는 경우 역할은 다음과 같다.

- **MCP-01 / #132:** 승인 설계와 출처를 담은 패킷을 구성·전달한다. 공유 기록을 받지 않으면 그 기록과의 충돌을 감지하지 않는다. #132에서는 패킷 구성·출처와 실제 MCP-01 연결을 확인하며, 공유 기록 비교 기능이 구현됐다고 가정하지 않는다.
- **기록 조회 도구:** MCP-05 `find_context`와 MCP-06 `read_context(RECORD)`는 권한 있는 기록의 목록·상세를 제공한다. 두 근거를 비교하거나 충돌을 판정하는 기능은 확인되지 않았다.
- **AI 에이전트:** MCP-01에서 승인 설계를 받고 별도 도구로 관련 SHARED 기록을 실제 조회해 두 근거를 모두 확보했을 때 비교·검토 필요 표시를 수행하는 주체다. 필요한 설계 변경은 MCP-04로 제안한다.
- **비비 / #135:** 오서현님은 승인 설계를 기준으로 답하고 관련 SHARED 기록과 충돌하면 출처를 구분해 검토 필요를 표시하는 방향에 동의했다. 비비 질문은 사람 세션이고 MCP-05·06은 에이전트 인증이므로 비비가 MCP 도구를 직접 호출한다고 가정하지 않는다. #135에서 사람 세션의 권한 있는 SHARED 기록을 제공할 BE 조회 경로, 충돌 판정·표시와 기록 ID·리비전의 응답 표현을 합의한다. 기존 `Source`와 제안된 `BeeCitation`은 문서 중심이므로 기록 출처를 그대로 표현할 수 있다고 가정하지 않는다.

두 근거 중 하나를 찾지 못했거나 조회에 실패하면 충돌이 없다고 단정하지 않는다. 에이전트·비비의 실제 비교와 연동은 아직 구현 확인 사항이며, 필요한 API·서비스·응답 계약 변경은 별도 합의한다.

전진님 리뷰에 따라, 공유 기록 제외를 채택하면 MCP-01 도구 설명에 **“공유 기록은 포함하지 않으니 필요하면 `find_context`로 확인”**을 넣는다. 안내만으로 별도 조회나 충돌 감지가 보장되지는 않는다. 비비의 조회 경로는 위 #135 확인 범위로 남는다.

**계약 합의 필요:** 승인 설계끼리의 충돌·빈칸을 MCP-01의 `unresolved`로 전달하는 방식과 #110의 공유 기록 패킷 제외 범위는 관련 담당자와 정한다. 공유 기록을 제외하면 MCP-01은 그 기록과의 충돌을 직접 판정하지 않는다. 패킷에 포함하는 방안은 #110의 확장 X7이다.

**근거·영향:** 기록과 후보의 권위를 승인 기준과 섞지 않기 위한 방향이다. 패킷 세부 범위와 충돌 처리 연결은 #110·#132·#135에 영향을 준다.

### 2.2 조회 수준과 출처 (C4)

**#95 정책 결정:** L0/L1/L2 대신 기록 목록 `find_context`의 **summary**와 `read_context(RECORD)`의 **detail**로 구분하고 별도 조회 수준 파라미터는 두지 않는다. 패킷은 MCP-01과 `read_context(PACKET)`으로 조회하며 개인 대화 원문은 제공하지 않는다.

**#95 정책 결정 — 길이 방향:** `summary`는 500, `detail`은 10,000 **Unicode 코드 포인트**를 상한으로 두고 초과 시 `400 validation_failed`로 거부한다. 변준성·전진님도 이 방향에 동의했다. 기준 dev의 `DesignContentValidator`·`ChangeDiscussionService`의 `String.length()` 및 `@Size`는 UTF-16 코드 단위이고, `DocumentInputValidator`·`ProposalValidator`의 일부 검증과 `RelationStorageService`는 `codePointCount`를 사용한다. 예를 들어 이모지 하나는 UTF-16에서 2, 코드 포인트에서 1로 센다. 공통 입력 검증과 API·서비스 계약 반영은 개발 전에 담당자와 정하고, 화면 안내와 한글·이모지 경계 테스트에도 반영한다. 기존 입력 계약은 변경 합의·반영 전까지 바뀌지 않는다.

기록 목록과 상세에는 작성자·리비전, `is_latest_revision`, `references_current`가 있다. 둘은 다른 값이며, 참조가 없어도 `references_current=true`일 수 있으므로 이를 승인 근거의 증거로 쓰지 않는다. 목록에는 `design_refs`와 문서 위치가 없고 상세의 `design_refs`도 설계 항목·버전 참조다. 문서 근거는 참조 가능한 패킷이나 원본에서 문서 ID·버전·위치를 확인하며, 확인하지 못하면 출처 부족으로 취급한다. 패킷은 두 기록 플래그 대신 `baseline_id`와 `sources`를 사용한다.

**근거·영향:** 기존 도구를 활용하되 출처와 현재성의 공백을 숨기지 않는다. #132의 조회·표현·크기 계약, MCP-05·06과 REST CTX 응답 및 입력 검증에 영향을 준다. 목록의 출처 제공, 패킷 현재성 표시, MCP-01 응답 잘림·전체 조회 경로는 별도 확인한다. 2.4절의 이력 검색 모드는 조회 **수준** 파라미터와 별개의 제안이다.

### 2.3 개인 기록의 수집·공유·보존 (C5\~C9·C12·C13)

#### C5 — 개인 기록 수집과 사용자 확인

MVP에서는 대화를 훅·로그로 자동 수집하지 않고 사용자가 명시적으로 제출한 `context_record`만 저장한다. `write_context`와 REST CTX-A04에서 공개 범위를 명시한다. 비비 대화 이어가기용 이력은 별개 쟁점이다 (C8).

MCP-07 설명에는 기록 내용과 공개 범위를 사용자에게 보여 주고 확인받을 것, SHARED는 되돌릴 수 없음을 안내하는 방향이다. 전진님 리뷰에 따른 적용 방향이며, 서버는 사람의 확인 여부를 강제하지 않는다. `visibility` 필수 입력이나 에이전트가 보낸 확인 플래그만으로 실제 동의를 증명할 수 없다. 도구·화면의 적용과 연결은 담당 작업에서 확인한다.

#### C6·C13 — 비밀값 검사 및 노출 사고 대응

비밀번호·토큰·API 키·환경 변수 원문·개인 키, 에이전트 내부 추론과 대화 원문은 기록하지 않도록 안내한다. 비밀값 입력 검사의 범위와 구현 방식은 담당자가 개발 과정에서 결정한다 (C6). 알려진 형식을 서버에서 거부하는 방법을 검토할 수 있지만 모든 비밀값을 찾아낼 수는 없다. 감사·애플리케이션 로그와 예외 메시지에 본문을 남기지 않는 안은 C7에서 확인한다.

MVP에서는 일반 공유 철회 기능을 제공하지 않는다 (C13). 기록 전에 “SHARED는 되돌릴 수 없음”을 안내한다. PRIVATE 후속 판을 만들거나 최신 판정을 바꿔도 이미 공개된 SHARED 본문과 사본은 사라지지 않는다.

일반 철회와 별도로, 비밀값·개인정보 노출 사고의 대응 방식과 구현 범위는 담당자가 개발 과정에서 검토한다. 양지훈님 리뷰처럼 신고 후 권한이 확인된 담당자가 조회·검색을 제한하고 정정·후속 처리를 정하는 방식이 검토 대상이다. MVP 제공 여부, 차단 수단·조건과 역할은 미정이며 구현도 확인되지 않았다. 기존 보안·보존 계약을 변경하려면 팀 합의가 필요하다.

담당자는 `context_record` 원본, 검색 결과와 향후 색인, `mcp_command` 멱등 응답 사본, 로그, 백업의 처리 범위를 각각 검토한다. 사본만 삭제하면 같은 키의 재요청이 새 쓰기로 처리되어 내용이 다시 저장될 수 있다. 재시도 응답 차단·재유입 방지와 24시간 멱등 계약의 관계를 함께 검토한다.

로그·백업 삭제 가능 시점과 이미 조회·전달·복사된 내용은 회수하지 못할 수 있다는 한계도 고려한다. UPDATE 차단·물리 삭제 금지 원칙의 예외, 리비전 참조·이력 영향과 요청·차단·승인·감사 담당은 미정이다. 사전 안내나 새 PRIVATE 리비전만으로 공개된 내용을 비노출 처리할 수 없다.

#### C12 — SHARED·PRIVATE 접근과 AI 활용

SHARED는 현재 프로젝트 멤버가 접근하고, PRIVATE는 작성자만 조회하는 기존 권한을 유지한다. 작성자 본인의 개인 AI 에이전트는 프로젝트 권한과 작성자 확인 후 `find_context`·`read_context`로 본인의 PRIVATE `context_record`를 조회·활용할 수 있다.

PRIVATE 기록은 다른 팀원의 AI와 팀 공용 컨텍스트, MCP-01 패킷·공유 임베딩 색인에 제공하지 않는다. 비비는 본인 작성분도 검색·AI 입력·답변 근거에서 제외한다. 오서현님도 비비의 제외 방향에 동의했다. 본인의 비비 대화 이력을 이어가기에 사용하는 C8은 별개다.

에이전트의 사용자 식별·권한 검증과 전달 경로는 기존 계약에 맞게 확인한다. 다른 프로젝트의 ID 참조·검색은 권한과 복합 FK로 제한하지만, 자유 텍스트에 복사한 정보까지 자동 판별하지는 못한다.

#### C9 — 탈퇴 후 기록 처리

탈퇴 회원의 SHARED 기록은 보존하고 작성자 이름을 “탈퇴한 사용자”로 표시한다. 이 결정은 이름의 표시 정책이며 `author_account_id` 변경이나 모든 식별 정보의 익명화를 뜻하지 않는다. 변준성님은 기록 응답 대신 멤버 표시 측에서 처리하자고 제안했다.

표시 경로·응답 계약과 ACC-06의 `context_record` 적용 범위는 개발 전에 확인한다. 혼자 사용하는 프로젝트를 탈퇴 시 삭제하는 Q05 기본안과의 관계, 프로젝트 삭제 시 SHARED 기록의 보존 범위·접근 방식도 확인한다.

PRIVATE 원본은 최종 보존·파기 정책을 정하기 전까지 접근 불가 상태로 보존하는 우선 방향이다. 무기한 보존이나 현재 탈퇴 처리의 구현 완료를 뜻하지 않는다. 개발 전 계속 보존, 탈퇴 시 파기, 일정 기간 후 파기와 보존 기간을 결정한다. 파기 선택 시 UPDATE 차단·물리 삭제 금지, `previous_id`·`root_id`와 참조 FK, 감사·멱등 사본 및 백업에 미치는 영향을 함께 결정한다. 탈퇴 계정의 `mcp_command` 사본 삭제는 4.3절에서 별도 검토한다.

#### C7 — 만료된 멱등 사본 정리

재요청이 없는 만료 `mcp_command` 행도 별도로 정리하는 방향이다. 24시간 만료가 물리 삭제를 보장하지는 않는다. 정리 시점·방식, 만료 전 재시도 보장과 실제 로그 설정은 개발·배포 전에 확인한다 (S3).

#### C8 — 비비 대화 이력 보존

오서현님은 창 종료·새로고침 후 본인만 이전 질문·답변을 확인하고 이어갈 수 있도록 이력을 보존하는 안에 동의했다. 이력은 SHARED 기록과 구분하고 자동 공유하거나 다른 사용자의 답변 근거로 사용하지 않는 방향이다.

Q13의 수정안 기본값은 창을 연 동안만이며, BEE-A01·A03은 대화 본문을 저장하지 않는다고 명시한다. 보존안을 채택하면 Q13·API 계약을 함께 변경해야 한다. 보존 기간, 사용자 삭제, 프로젝트 제외·회원 탈퇴·프로젝트 삭제 후 접근과 보존은 #135에서 구현 전 합의한다. 문서 보완 제안에 귀속되는 DOC-A22 대화는 별도 기록 목적이므로 적용 범위를 구분한다.

기록 단위의 명시적 제출과 비밀값 노출 최소화가 목적이다. 실제 확인 강제·검사·보존을 채택하면 MCP/REST 입력, UI, 로그·멱등 응답 저장 및 #135에 영향을 준다. 기존 권한을 유지하고 C12의 도구 설명 반영 범위는 구현 계약과 함께 확인한다.

### 2.4 PRIVATE와 리비전 최신 판정 (C3·C10·C11)

#95 정책 결정은 같은 기록 체인의 공개 범위 고정, 기본 검색의 최신 판 반환, MVP 이력의 `previous_id` 순회다. 기존 혼합 체인의 PRIVATE 존재·ID 노출은 별도로 확인한다. 변준성님과 전진님도 새 쓰기·검색 방향에 동의했다. 기존 혼합 데이터 처리나 API·서비스 계약 변경이 합의·구현됐다는 뜻은 아니다.

| 결정 축 | 정책 방향 | 영향과 개발 전 확인 사항 |
| --- | --- | --- |
| 공개 범위 (C3·C10) | 후속 판은 이전 판과 같은 `visibility`만 허용한다. 변경 요청은 400 `validation_failed`다. PRIVATE 메모를 공유하려면 새 SHARED 기록을 쓴다. | 균일 체인은 보이는 최신 판과 전체 최신 판이 같고 비공개 판 혼합으로 인한 노출을 막는다. 새 SHARED는 별개 체인이라 PRIVATE 이력이 자동 연결되지 않는다. 사용자 안내와 기존 권한·충돌 검사·멱등 재생 순서를 확인한다. |
| 이력 (C11) | 기본 검색은 `query` 필수·최신 판만 반환한다. MVP 이력은 `read_context`의 `previous_id`로 조회한다. | 권한이 있는 이전 판만 순회한다. 최신 판이 검색어에 맞지 않으면 체인을 찾지 못한다 (V15). 기존 혼합 체인은 PRIVATE 판의 404에서 순회가 끊길 수 있다. 공개 범위 고정과 최신 검색은 별도 변경이다. |
| 이력 확장 (C11) | 변준성·전진님은 전진님의 `root_id` 이력 모드 제안을 MVP 이후로 미루는 데 동의했다. 확장안은 `root_id` 필수·`query` 선택·`revision_no desc`다. 첫 판의 DB `root_id`는 NULL이므로 `coalesce(root_id, id)`가 필요하다. | 검색어가 다른 이전 판도 찾지만 요청·권한·정렬·페이지 계약 변경이 필요하다. 기존 `id < cursor`와 함께 쓰려면 ID·리비전 순서의 일치가 항상 성립함을 입증·테스트하거나 정렬에 맞는 커서를 정해야 한다. |

**현재 구현과 차이:** `ContextLookup.superseded`는 조회자에게 보이는 직접 후속 판만 확인한다. `SHARED rev1 → PRIVATE rev2`에서 다른 멤버는 rev1을 최신으로 본다. `SHARED rev1 → PRIVATE rev2 → SHARED rev3`에서는 rev1과 rev3이 모두 최신으로 보일 수 있다. PRIVATE 후속 판의 존재를 숨기려는 구현이지만 오래된 공유 판이 현재 근거로 쓰일 수 있다.

혼합 체인의 SHARED 응답에서 `root_id`·`revision_no`와 상세 `previous_id`는 PRIVATE 이전 판의 존재나 ID를 드러낼 수 있다 (C10). PRIVATE 본문은 404지만 이 메타데이터 노출은 기존 비노출 계약과 어긋난다. 기존 데이터가 있으면 임시 응답 가림 등 비노출 계약을 지키는 처리와 데이터 처리 방식을 개발 전에 정한다. 비노출 예외는 확정하지 않는다.

기존에 검토한 체인 전체 최신 판정안(C3)은 채택하지 않았다. 혼합 체인에서는 최신 여부나 검색 결과·`has_more` 변화로 PRIVATE 후속 판 존재를 추론할 수 있기 때문이다. 기본 검색은 검색어·작업·종류 조건과 별개로 후속 판을 확인한다. 권한·최신 판 필터는 페이지·`has_more` 계산 전에 적용하며, 조회·페이지 계약은 개발 전에 확인한다.

**기존 데이터:** 새 후속 판의 공개 범위 변경 금지는 이미 저장된 혼합 체인에 소급되지 않는다. 전진님이 제안한 다음 조회는 해당 DB에서 이전 판과 공개 범위가 다른 인접 리비전 쌍의 수를 확인한다.

```sql
select count(*) from context_record n
  join context_record p on p.id = n.previous_id
 where n.visibility <> p.visibility;
```

결과가 0이면 참조 관계가 정상인 해당 DB에는 조회 시점의 혼합 체인이 없어 기존 데이터 처리 논의를 생략할 수 있다. 배포 중 구버전 쓰기나 진행 중인 요청이 새 혼합 체인을 만들 수 있으므로 종료 후 다시 확인한다. 0이 아니면 UPDATE 차단과 참조 관계를 고려해 비파괴 처리와 임시 노출 방식을 합의한다. 기존 PRIVATE 404·검색 제외·불변 리비전·409는 유지한다. MCP-05·06/REST CTX, `ContextLookup`, 검색·페이지 및 테스트가 영향받으며, 최신 판정은 C13의 공유 철회를 대체하지 않는다.

### 2.5 개인 맥락 기능과 MVP 범위 (C14)

CTX-07\~09·11·12의 원문과 각 요구사항의 실제 범위가 확인되지 않았다. 개인 에이전트의 메모·대화 요약을 저장·검색하고 공유로 승격하는 **확장**으로 가정해, 자동 수집·개인 의미 검색·계층 승격을 우선 후속으로 검토하는 방안을 추천한다. 기존 명시적 `context_record` 기록과 기본 불변 패킷 저장을 이 가정으로 제외하지 않는다. 2.3절에서 허용한 작성자 본인의 기존 PRIVATE 기록 조회·활용과 확장의 자동 수집·의미 검색은 구분한다.

POL-12·13의 우선순위 추천과 개인 기록 없이 첫 작업이 가능해야 하는 AC-01은 참고 근거지만, 원문이나 MVP 범위를 확정하는 근거는 아니다. **원문·작성자와 범위 결정 담당자를 확인한 후 요구사항별 포함 여부를 결정한다.** 확장을 추진한다면 저장소 재사용, 사용자별 검색 격리, 사람이 확인한 요약의 공유 승격, 보존·삭제와 효과 측정을 별도 결정한다. 이 결과는 #110의 X7 및 #132·#135의 입력 범위에 영향을 줄 수 있다.

### 2.6 효과 검증 방향 (C15)

**#95 정책 결정:** FE–BE API 필드, AI 출력–BE 입력, 미정 정책, 동시 계약 변경의 네 문제 유형을 각 2건씩 구성하고 정상 대조 2건을 더해 효과와 비용을 검증한다. 사례 작성자가 아닌 팀원이 실험 전에 기대 판정과 근거를 작성한다. 정밀도·재현율·불필요한 검토율·소요 시간·토큰/비용을 기록하며 측정하지 않은 절감률은 단정하지 않는다.

**해석 범위:** 10건은 MVP 단계의 초기 검증이다. 각 조건에서 실제 측정한 정밀도·재현율·불필요한 검토율·소요 시간·토큰 비용을 표본 수와 함께 보고하고, 사례별 결과와 해석을 구분한다. 표본이 적으므로 일반적인 성능 보장이나 확정적인 개선율로 해석하지 않는다. 분모가 없어 계산할 수 없는 지표는 계산 불가로 표시한다.

**근거·영향:** 문제 유형과 정상 사례를 함께 살펴보며 사후 정답 조정을 막기 위한 구성이다. #141에서 실제 사례·참여자·일정·실행 조건·목표 수치·측정 방법을 확정한다. 실험 구성 결정은 검증을 수행했거나 효과가 입증됐다는 뜻이 아니다.

### 4.3 구현 계약과 운영 확인

정책 방향 자체를 다시 합의하는 항목이 아니다. 아래 세부 사항은 각 항목의 시점에 따라 관련 담당자가 개발 전이나 개발 과정에서 정한다. 필요한 기존 계약 변경은 반영 전에 관련 담당자와 합의한다.

- **C2 연동 계약:** 2.1절의 역할 구분에 따라 #132는 패킷 구성·MCP-01 연결 범위를, #135는 비비의 사람 세션에서 권한 있는 SHARED 기록 조회·비교·기록 ID와 리비전 및 충돌 표시 경로를 확인한다. #110의 패킷 범위와 `unresolved` 내용, 필요한 BE·출처 응답 계약 변경은 전진·변준성과 각 작업 담당자가 합의한다. V5a는 공유 기록 제외 계약을 채택한 경우의 검증이다.
- **C4 길이·출처:** 관련 담당자와 공통 입력 검증·API 계약 적용을 정한다. 문서 출처와 패킷 현재성 표시도 확인한다 (2.2절, S4·#132).
- **C5·C12 적용:** MVP의 사용자 확인 안내와 서버 미강제 방향은 2.3절을 따른다. 개인 AI 에이전트가 작성자와 프로젝트 권한을 확인해 본인 PRIVATE 기록만 조회·활용하는 경로, 타인의 AI·공유 경로 및 비비의 제외 범위를 확인한다. MCP-05·06·07 설명, 화면 연결 및 #135의 전달 범위에 필요한 계약 변경은 관련 담당자와 정한다 (S1).
- **C6 비밀값 검사:** 담당자가 개발 과정에서 검사 여부·범위·방식과 오탐을 결정한다. MCP·REST 적용은 S2를 확인한다.
- **C13 사고 대응:** 담당자가 개발 과정에서 대응 방식과 MVP 구현 범위, 저장·재시도 영향을 검토한다 (2.3절). 기존 보안·보존 계약을 변경하려면 팀 합의 후 반영한다. C3은 공유 철회를 대체하지 않는다.
- **C7 기록 본문:** 변준성님이 제안하고 전진님이 동의한 만료 행 정리의 주기·방식과 재시도 보장을 관련 구현 담당자와 확인한다. 로그·예외·감사의 본문 노출도 배포 전에 확인한다 (S3). 전진님은 서버가 prod 프로필로 실행된다고 설명했으며 실제 활성 프로필과 로그 설정은 배포 환경에서 확인한다.
- **C9 멱등 사본:** 변준성님은 계정 탈퇴 시 해당 계정의 `mcp_command` 사본을 삭제하겠다고 제안했다. 이는 PRIVATE 기록 원본의 보존·파기 결정과 별개다. 모든 프로젝트·MCP 동작에 걸친 삭제 범위, 탈퇴와 진행 중 쓰기의 경합, 24시간 재시도 계약 및 탈퇴 처리와의 연계를 합의·검증한다.
- **C15 실험 실행:** 정해진 10건 구성에 따라 양지훈과 #141에서 구체 사례, 참여자·정답 작성자, 일정, 실행 조건, 통과 목표와 비용 측정 방법을 확정한다. 11/10\~11/13 일정과 같은 모델·요청문으로 BEEZ 사용(MCP-01 + 검증) 및 승인 문서만 제공한 미사용 조건을 비교하는 방식은 제안이다. 난이도와 검토 조건을 맞추고 계획 단계 탐지와 실제 구현 예방은 구분한다.

**후속 처리:** 합의 결과와 날짜를 PR에 남기고, 의견이 다르면 관련자와 개발팀이 논의한다. 최종 결정자·절차는 미확인이다. 합의된 계약 변경은 해당 설계·API와 Jira 담당 작업에 별도로 반영한다. 제품 내 프로젝트 LEADER의 설계 변경 승인 규칙 APR-07은 개발팀의 PR 승인자를 지정하는 근거가 아니다. 실제 MCP-01 통합은 #131·#132와 #166, MCP 연결 #176\~179 및 #141 검증의 준비 상태를 별도로 확인한다.

V7·V8·V12의 기대 결과는 PRIVATE 존재 추론을 허용하는 별도 계약 합의 없이는 적용하지 않는다. V12는 이력 전체 조회 계약도 전제로 한다. 새 쓰기의 공개 범위 변경을 금지하면 V7·V8·V9·V12·V14의 혼합 체인은 기존 데이터 fixture로 준비한다. 별도 조건이 없는 검색 사례에서는 반환을 기대하는 리비전의 요약이 검색어와 일치하고 한 페이지에 들어간다.

### 권한과 접근

**V1**

- 조건·입력: A, B는 같은 프로젝트 멤버. A가 PRIVATE 기록을 작성하고 권한 있는 A의 개인 AI 에이전트가 `read_context(RECORD, id)`와 `find_context(query)`를 호출한다. B의 AI 에이전트도 같은 기록에 접근한다.
- 기대 결과: A의 에이전트는 A의 기록을 조회·활용할 수 있다. B의 에이전트에는 404 `not_found`이고 검색 결과·`has_more`에 없다.
- 실패 조건: A의 권한 있는 조회가 거부되거나, B에게 내용이 제공되거나 403·건수 차이로 존재가 드러남
- 확인 증거: 에이전트 사용자·프로젝트 권한 및 조회 통합 테스트, 응답 본문

**V2**

- 조건·입력: A가 속한 프로젝트의 조회 경로에서 접근 권한이 없는 다른 프로젝트 C의 기록 ID로 `read_context`
- 기대 결과: 404
- 실패 조건: 내용·존재 노출
- 확인 증거: 통합 테스트

**V3**

- **기존 동작 — 프로젝트 제외:** A가 SHARED 기록을 작성한 뒤 프로젝트에서 제외된다. 남은 멤버가 기록을 조회하고 A의 에이전트 토큰으로 접근을 시도한다. 기록과 `author_account_id`는 반환되고 A의 프로젝트 접근은 거부된다. 기록 응답에서 작성자 표시명은 제공하지 않으므로 화면의 표시명 유지는 검증 대상으로 단정하지 않는다.
- **C9 계약 확인·구현 후 — 계정 탈퇴:** A가 SHARED 기록을 작성한 뒤 계정을 탈퇴하고 남은 멤버가 조회한다. 기록은 보존되고 사용자에게 작성자 이름이 “탈퇴한 사용자”로 표시된다. 표시 경로와 응답 계약은 개발 전 확인 대상이다. 프로젝트 제외만으로 계정 탈퇴 표시를 요구하지 않는다.
- **실패 조건:** 기존 동작에서 제외된 A가 계속 접근하거나 남은 멤버가 기록을 볼 수 없음. C9 적용 후에는 기록이 사라지거나 정한 작성자 이름 표시가 적용되지 않음.
- **확인 증거:** 기존 권한·응답 통합 테스트와, C9 적용 후 탈퇴·표시 경로의 통합 또는 화면 테스트. 후자의 현재 구현은 확인되지 않았고 검증은 미실행이다.

**V4**

- 조건·입력: A가 PRIVATE 기록 작성. B 요청으로 MCP-01과 비비에 질문하고, A 본인도 비비에 질문한다. 비비의 C12 적용 후 검색·AI 입력·답변을 확인한다.
- 기대 결과: 패킷과 비비의 검색·AI 입력·답변 근거에 A의 PRIVATE `context_record`가 없다. A의 비비 대화 이력을 C8 합의에 따라 이어가기에 사용하는 것은 별개다.
- 실패 조건: 본인 또는 타인의 PRIVATE 기록이 비비 검색·AI 입력·답변 근거에 포함되거나 패킷에 나타남
- 확인 증거: 패킷 `content`, 비비 검색 결과·AI 입력·응답 근거

### 근거 충돌과 비밀값

**V5a**

- 조건·입력: MCP-01에서 공유 기록을 제외하는 별도 계약의 합의·적용 후. 현재 기준의 승인 설계 항목에 API 필드 `memberId`가 있고 SHARED `DECISION` 기록에는 `userId`가 있다. 요청 자체에는 공유 기록 내용이 없다. MCP-01 요청
- 기대 결과: 승인 API가 `design_items`에 있고, 기록은 패킷 어디에도 없음. 기록과의 충돌을 `unresolved`에 넣지 않음
- 실패 조건: 기록 내용이 `design_items`·`constraints`·`unresolved`에 등장
- 확인 증거: 패킷 `content`

**V5b**

- 조건·입력: V5a와 같음. 에이전트가 `find_context`로 기록 조회
- 기대 결과: 기록이 `kind=DECISION`, 작성자·리비전·`references_current`와 함께 반환됨. 에이전트는 승인 API(`memberId`)로 구현하거나 MCP-04 변경 제안으로 넘김
- 실패 조건: 기록을 근거로 승인 계약과 다르게 구현
- 확인 증거: 도구 응답, 에이전트 작업 기록 (#141 수동 확인)

**V5c**

- 조건·입력: V5a와 같음. 비비에게 "로그인 응답 필드가 뭐야?"
- 기대 결과: 승인 API를 답으로 주고, 기록을 함께 찾았다면 두 출처를 보이며 "검토 필요" 표시. 기록을 찾지 못하거나 조회에 실패하면 충돌이 없다고 단정하지 않음
- 실패 조건: 기록 내용을 확정 답으로 제시
- 확인 증거: 비비 응답 근거 (#135 대표 질문 세트)

**V6**

- 조건·입력: C6에서 `ghp_` 형식 검사를 선택하고 S2를 도입한 경우. `detail`에 해당 토큰 형식 문자열 입력
- 기대 결과: 400 `validation_failed`, 저장 없음, 로그에 원문 없음
- 실패 조건: 저장되거나 로그에 남음
- 확인 증거: 테스트, 로그

### 리비전과 이력

**V7**

- 조건·입력: 기존 문서의 체인 전체 최신 판정 및 이력 검색안이 합의·적용된 경우. 기존 데이터 또는 혼합 허용 정책에서 A의 SHARED rev1 뒤 PRIVATE rev2가 있다. B가 기본·이력 `find_context`, `read_context(RECORD, rev1·rev2)`를 호출한다.
- 기대 결과: 기본 검색에는 이 체인이 없음. 이력 검색과 rev1 직접 조회에는 rev1이 `is_latest_revision=false`로 보임. rev2는 404·검색 제외. 컨텍스트·비비가 rev1을 현재 근거로 쓰지 않음 (C3, 2.4절)
- 실패 조건: 기본 검색에 rev1이 나오거나 rev1이 `true`, rev2 내용이 노출됨
- 확인 증거: 통합 테스트

**V8**

- 조건·입력: V7과 같은 판정·이력안에서 기존 혼합 데이터 또는 혼합 허용 정책의 SHARED rev1 → PRIVATE rev2 → SHARED rev3이 있다. B가 기본·이력 `find_context`, rev1·rev2·rev3 `read_context`를 호출한다.
- 기대 결과: 기본 검색에는 rev3만 나옴. 이력 검색과 직접 조회에서 rev3은 `true`, rev1은 `false`, rev2는 404·검색 제외 (C3, 2.4절). 현재 동작: rev1·rev3 모두 `true`
- 실패 조건: 기본 검색에 rev1이 나오거나 한 체인에서 `true`가 둘 이상, rev2 내용이 노출됨
- 확인 증거: 통합 테스트

**V9**

- 조건·입력: V8의 혼합 체인에 대해 A 본인이 열람 가능한 각 리비전을 조회한다. 현행 및 C3 적용 후의 회귀 확인이다.
- 기대 결과: A에게는 rev3만 `is_latest_revision=true`다. C3의 체인 전체 판정안을 채택한 경우에만 V8의 B 결과와 최신 판이 일치하는지도 별도로 확인한다.
- 실패 조건: A에게 최신 판이 둘 이상이거나 rev3이 최신이 아님. C3 체인 전체 판정안을 채택한 경우 A·B 결과가 다름.
- 확인 증거: 통합 테스트

**V10**

- 조건·입력: S6의 최신 기본 검색 및 이력 방식 도입 시. A가 SHARED rev1 → SHARED rev2. B가 기본 검색과 채택한 이력 조회를 수행한다.
- 기대 결과: 기본 검색은 rev2만 반환한다. MVP에서는 rev2 상세의 `previous_id`로 rev1을 찾아 `read_context`로 읽는다. 별도 이력 검색을 향후 합의·도입한 경우에는 rev1·rev2의 ID 반환과 각 판의 상세 조회도 확인한다.
- 실패 조건: 기본 검색에 같은 체인의 리비전이 둘 이상 반환되거나 채택한 이력 조회 방식으로 rev1에 도달하지 못함
- 확인 증거: 통합 테스트

**V11**

- 조건·입력: C9의 접근 불가 상태 우선 보존 방향에 필요한 계약을 합의하고 S7을 도입한 경우. A가 PRIVATE 기록 작성 후 탈퇴. 제품의 프로젝트 LEADER가 `read_context`, `find_context`
- 기대 결과: 404·검색 제외. 기록 행은 DB에 남음
- 실패 조건: 프로젝트 LEADER가 열람 가능하거나 행이 삭제됨
- 확인 증거: 통합 테스트, DB 조회

파기안 선택 시에는 탈퇴 시점 또는 보관 기간 경과 후의 파기, 참조·멱등 사본과 탈퇴·쓰기 경합을 별도 검증한다. 기대 결과는 선택한 계약을 따른다.

**V12**

- 조건·입력: 체인 전체 최신 판정과 별도 이력 검색안을 합의·적용한 경우. 기존 혼합 데이터 또는 혼합 허용 정책에서 A의 SHARED rev1 → SHARED rev2 → PRIVATE rev3 → SHARED rev4가 있다. B가 이력 `find_context`로 체인을 조회하고 반환된 ID를 `read_context`로 조회한다. 테스트에서 미리 아는 rev3 ID로도 직접 조회한다.
- 기대 결과: rev1·rev2·rev4의 ID를 찾고 각각 직접 조회 가능. rev3은 404·검색 및 건수 제외
- 실패 조건: rev2를 찾지 못하거나 rev3 내용·건수가 노출됨
- 확인 증거: 통합 테스트

**V13**

- 조건·입력: 최신 공유 기록 하나는 이전 기준의 설계 버전을 참조하고 다른 하나는 설계 참조가 없다. 두 기록을 조회한다.
- 기대 결과: 첫 기록은 최신 리비전이어도 `references_current=false`로 표시한다. 참조 없는 기록의 `references_current=true`만으로 승인 설계 근거라고 판단하지 않는다.
- 실패 조건: 최신 여부만으로 오래된 참조를 현재로 취급하거나 참조가 없는데 승인 근거라고 표시한다.
- 확인 증거: 통합 테스트, 조회 응답 및 소비자 판정 결과

**V14 — 비공개 이전 판의 메타데이터 (C10)**

- 조건·입력: 기존 혼합 데이터 또는 혼합 허용 정책에서 A의 PRIVATE rev1 뒤 SHARED rev2가 있다. B가 rev2를 목록·상세 조회하고 테스트에서 아는 rev1 ID로 직접 조회한다.
- 기대 결과: rev1 본문은 404다. rev2의 `root_id`, `revision_no`, `previous_id`는 기존 PRIVATE 비노출 계약을 지키도록 C10에서 합의한 방식으로 반환하거나 가린다.
- 실패 조건: PRIVATE 본문 또는 합의하지 않은 메타데이터가 노출되거나, 합의한 응답 형태를 지키지 않는다.
- 확인 증거: 권한·응답 계약 테스트

**V15 — 검색어가 최신 판에 없는 경우 (C3·C11)**

- 조건·입력: C3·C11의 최신 판 기본 검색안 합의·적용 후. SHARED rev1의 요약만 `로그인`을 포함하고 후속 SHARED rev2에는 그 단어가 없다. 다른 일치 기록이 없다. B가 `로그인`으로 기본 검색하고, 이력 조회 방식은 채택안에 따라 확인한다.
- 기대 결과: 기본 검색은 **0건**이다. 이력 검색 모드를 채택한 경우 이력 검색에서 rev1을 찾을 수 있다. `previous_id` 순회안을 채택한 경우 rev2의 ID를 별도로 알고 있어야 상세 조회를 통해 rev1에 도달할 수 있다.
- 실패 조건: 검색 조건에 맞는 판만 비교해 rev1을 최신으로 반환하거나, 채택한 이력 조회 방식으로 허용된 과거 판에 도달하지 못한다.
- 확인 증거: 검색·페이지 경계 통합 테스트

**V16 — 새 리비전의 공개 범위 고정안**

- 조건·입력: 공개 범위 고정 방향에 필요한 계약을 합의·적용한 후, 작성자가 권한이 있고 기존 후속 판 충돌이나 멱등 응답 재생이 선행하지 않는 새 쓰기로 SHARED → PRIVATE와 PRIVATE → SHARED 후속 판을 각각 시도한다. 같은 범위의 후속 판 생성과 같은 이전 판 동시 수정도 시도한다.
- 기대 결과: 양방향 변경은 `400 validation_failed`, 같은 범위의 정상 수정은 성공하고 같은 이전 판 경쟁은 기존 `409 revision_conflict`를 유지한다. 타인의 PRIVATE 조회·수정은 기존 404다.
- 실패 조건: 범위 변경이 저장되거나 기존 권한·리비전 충돌 계약이 깨진다.
- 확인 증거: 권한·동시성·입력 검증 통합 테스트

**V17 — 비밀값·개인정보 노출 사고 (C13)**

- 조건·입력: 담당자가 조회·검색·재시도 응답 제한과 정정 절차를 포함하는 MVP 사고 대응 경로를 선택·구현하고, 필요한 계약 변경에 팀 합의한 경우. 비밀값 또는 개인정보가 든 SHARED 기록과 멱등 응답 사본이 존재하며 권한 있는 담당자에게 사고가 접수된다.
- 기대 결과: 결정된 조회·검색·재시도 응답의 추가 노출 제한 및 정정 절차가 적용되고, 재요청으로 내용이 다시 저장되지 않도록 결정된 처리가 동작한다. 원본·사본·로그·백업의 처리 결과와 이미 전달된 내용의 한계를 정한 방식으로 확인한다.
- 실패 조건: 결정된 차단 경로에서 노출이 계속되거나 재요청으로 내용이 다시 저장됨. 사본·백업의 처리 상태를 확인하지 않고 모두 회수했다고 표시함.
- 확인 증거: 권한·조회·재시도 통합 테스트와 사고 처리 기록. 대응 방식 결정 및 필요한 계약 합의 전에는 검증 기준이 확정되지 않았다.
