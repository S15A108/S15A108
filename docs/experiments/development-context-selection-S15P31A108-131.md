# #131 개발 컨텍스트 선택 시나리오와 인공 후보

## 목적과 범위

[#130 개발용 나래 문서 4종](../../ai/evaluations/data/questions.json)을 이용해 #131의 선택·의존 확장과 오류 구분을 점검할 대표 사례를 준비했다. 입력과 독립 기대값은 [시나리오 fixture](../../ai/tests/fixtures/retrieval/context-selection-131.json)에 있다. 설계 항목·관계·작업 계획 참조와 선택 결과는 이 문서를 바탕으로 **인공으로 만든 개발용 데이터**다. 해당 항목이나 관계가 실제 발행됐다는 뜻이 아니다. 원문 인용은 #130 데이터에 존재하는 문장을 사용한다. 라벨은 작성자가 만든 초안이며 독립 사람 검토가 필요하다.

fixture의 `snapshot`은 BE가 권한과 현재 기준을 확인해 전달했다고 가정한 입력이고, 각 `fake_proposal`은 선택 공급자의 모의 출력이다. 모의 선택 테스트만으로는 실제 의미 검색·LLM 호출·BE/DB 연동이나 검색 정확도를 평가할 수 없다. 아래 임베딩 실험도 동일한 가상 후보를 직접 전달했으며 BE 색인과 운영 품질을 평가하지 않았다.

## 대표 요청과 기대 결과

| 사례 | 입력 및 인위적 선택 | 기대 결과 |

`irrelevant-allowed-id-negative-example`은 **의도적인 혼입**이다. 업로드 생성 요청에서 GET 목록 항목 `1103`과 `e-get`을 선택해도 두 ID가 허용된 후보에 속하기 때문에 단순 부분집합 검사는 이를 막지 못한다. 이 사례는 관련성 검증의 한계를 드러내며 무관 후보가 자동으로 배제됐다는 근거가 아니다. 유의미한 품질 평가는 별도 정답 라벨의 독립 검토와 실제 검색·선택 결과 측정이 필요하다.

## 실행과 해석

입력 구성 시 각 시나리오의 `request`, 선택적 `task_id`·`task_design_refs`·`search_status`로 `snapshot`의 해당 필드를 덮어쓴다. `evidence_override`가 있는 경우에만 증거 목록을 교체한다. `fake_proposal`은 `SelectionProposal`로 변환해 모의 공급자가 반환한다. `expected_design_items`의 순서는 기준 후보 목록 순서이며 `expected_evidence_ids`는 공급자가 선택한 순서다. 오류 사례는 코드와 호출 횟수를 확인한다. 혼입 사례는 `expected_irrelevant_ids`가 실제 결과에 남는 것을 확인하는 음성 대조군이다.

시나리오에 쓰인 원문은 `document_paths`의 각 파일에서 직접 확인할 수 있다. 버전·프로젝트 ID와 청크 ID는 시험 식별자다. 정책·문서 원문·AI 선택을 별도 출처로 취급하며, 본 테스트의 정상 여부와 별개로 MCP-01의 실제 인증, 색인 READY, 관계 조회 및 최종 baseline 재검사는 BE 통합에서 검증해야 한다.

## 임베딩 선택 예비 실측

2026-10-30에 선택기 기준 커밋 `131e614`에서 가상 시나리오 5건을 `text-embedding-3-small` 1024차원으로 실행했다. 임계값 0.65와 항목·근거 각각 최대 2개는 실험 설정이며 운영 기준이 아니다. 호출 10회, 입력 1,157토큰이 기록됐다. [원시 결과](results/S15P31A108-131-selection-pilot.json)에는 선택·누락·추가 ID와 호출별 사용량이 있다.

| 사례 | 결과 |
| --- | --- |
| 업로드 생성 | 기대 설계 `1101`, `1102`와 근거 `e-limit`, `e-post`가 모두 누락됐다. |
| 작업 계획 반영 | 작업 참조 `1104`만 반환하고 위 설계와 근거는 누락됐다. |
| 소유자 참조, 재시도 원문, 보관 기간 미정 | 이 fixture의 기대 ID 또는 `NO_MATCH`와 일치했다. |

이 다섯 건에서 기대 목록 밖 추가 ID는 기록되지 않았지만, 초안 라벨의 독립 검토가 없고 사례 수도 적어 무관 항목이 섞이지 않는다고 결론 내릴 수 없다. 업로드 두 사례의 누락 때문에 이 임계값의 실사용 적합성도 입증되지 않았다. 실측 당시에는 작업 참조만 반환돼도 `NO_MATCH`가 빠졌으며, 이후 해당 결함을 수정하고 회귀 테스트를 추가했다. 원시 결과는 수정 전 결과로 보존했으며 수정 후 재실측을 뜻하지 않는다.

다음 단계는 독립 검토한 사례로 선택 기준과 누락·혼입을 평가하고, BE의 실제 검색·권한 검증 및 관계·작업 참조를 연결한 통합 결과를 확인하는 것이다. 요청의 누락·충돌 의미 판별도 별도로 남아 있다.

## 임계값 비교 재측정 (2026-11-02)

같은 가상 사례 5건과 `text-embedding-3-small` 1024차원, 설계·근거 각각 최대 2개로 다시 측정했다. 실제 GMS 임베딩 호출은 **10회**, 기록된 입력은 **1,157토큰**이며 실패한 호출은 없었다. 기준 0.65와 비교값 0.45·0.50·0.55·0.60·0.70은 **동일한 임베딩 응답을 메모리에서 재사용**해 선택기를 다시 실행했다. [결과 JSON](results/S15P31A108-131-thresholds-2026-11-02.json)에 각 값의 선택·누락·추가 ID와 실제 호출 usage를 보존한다.

| 사례 | 관찰 |
| --- | --- |
| 업로드 생성 | 0.65에서는 기대 설계 `1101`·`1102`와 근거 `e-limit`·`e-post`가 모두 누락됐다. 0.45~0.55에서는 두 설계가 반환됐지만 두 근거는 여전히 빠지고 무관한 목록 조회 근거 `e-get`이 들어왔다. |

임계값을 낮추는 것만으로 두 업로드 사례의 누락과 혼입을 함께 해결하지 못했다. 0.65 재측정의 작업 계획 사례는 직접 매칭이 없어 `NO_MATCH`도 반환한다. 기존 10월 30일 기록은 수정 전 결과이므로 원본을 바꾸지 않았다. 이 비교는 자체 작성한 가상 라벨과 소수의 후보를 사용하며, 실제 BE 색인·권한·운영 데이터나 독립 검토된 정답을 검증하지 않는다. **어떤 비교값도 운영 임계값으로 채택하지 않았다.** 다음에는 독립 검토한 라벨과 별도 사례에서 후보 검색과 표현 방식을 함께 평가한다.
