# CDC 발행 수신·초기화·처리 큐 초안

> **합의 후 주의:** 아래 outbox·별도 작업 큐는 기존 실험 이력이다. 운영 계약은 #197 접수행을 분석 상태의 단일 기준으로 삼는다. 최초 v1과 197 이전 발행의 백필은 `NOT_EVALUATED`로 자동 분석하지 않고, 변경 발행의 `PENDING`만 분석 후보로 본다. 최초 관계 구축과 색인은 각각 #167·#223 경로다. 실제 197 테이블과 consumer, 원자적 claim·lease 및 자동 워커는 미연결이다. 이벤트 상태는 재전달 시 낡을 수 있으므로 실행 전 반드시 현재 접수행을 조건부 선점해야 한다.


**현재는 테스트용 기반이며 자동 동기화 기능은 완성되지 않았다.** 운영 DB나 Kafka를 자동 구성하지 않고, 관계 조회·AI 영향 분석·결과 저장을 실행하는 운영 워커도 없다. 이하 기존 outbox 경로는 명시적인 실험 모드에서만 사용한다.

## 발행 이벤트 접수

기존 outbox 실험 수신기는 기본 OFF다. 격리된 실험에서 활성화하려면 `beez.cdc.legacy-outbox-poc-enabled=true`, `beez.cdc.enabled=true`, `beez.cdc.bootstrap-servers`, `beez.cdc.group-id`, `beez.cdc.topic`을 명시해야 한다. `enabled=true`만 설정하면 #197 consumer가 아직 없다는 오류로 시작이 중단된다. 실험 플래그는 최초 발행의 구형 outbox 생성도 켜므로 운영에서 사용하지 않는다. Kafka consumer는 `beez.cdc.kafka-security.properties`로 SSL 또는 SASL_SSL 보안 설정을 받을 수 있다. 미설정 시 로컬 PLAINTEXT이므로 운영에서 사용하지 않는다. 인증 정보는 Git 밖의 비밀 저장소에서 주입하고 실제 TLS 연결을 검증해야 한다.

Debezium Outbox 행의 insert(`c`)와 snapshot(`r`)을 받는다. JSONB는 문자열/객체 모두 파싱하고, schema가 있는 wrapper와 없는 형식을 지원한다. Kafka tombstone과 Outbox 삭제는 새 발행이 아니므로 무시한다. 허용하지 않은 이벤트나 잘못된 프로젝트·버전·ID는 수신 실패로 취급한다. 이벤트의 원문 및 민감정보는 기록 대상이 아니다.

`INITIAL`과 `CHANGE` 모두 `cdc_publication_inbox`에 `PENDING`으로 기록하며, 같은 트랜잭션에서 `cdc_processing_job`에 `PUBLISHED_SYNC` 작업을 생성한다. 해당 DB 트랜잭션이 커밋된 후에만 수신기가 정상 반환하므로 Kafka RECORD offset 커밋보다 앞선다. 이벤트 ID와 payload가 모두 같은 재전달은 중복 기록하지 않고, 같은 ID에 다른 내용이 오면 오류다. bootstrap과 실시간 이벤트의 동일한 `(project_id, baseline_id, job_type)`도 작업 한 건만 생성한다. 이는 정확히 한 번 전송을 의미하지 않는다.

현재 Kafka 파싱·DB 접수 실패는 **전송/수신 장애**로, 해당 partition 레코드를 무한 재시도하며 뒤를 진행하지 않는다. 아래의 업무 처리 3회 재시도와는 별도다. Kafka offset 실패, 장애 복구, 관측·알림, 자동 DLQ·스킵은 아직 검증·구현하지 않았다.

## 초기 접수와 프로젝트별 큐

`PublicationBootstrapService`는 호출자가 명시적으로 프로젝트별 발행 baseline을 읽어 초기 작업을 등록하는 내부 서비스다. 후보를 읽은 뒤 새 버전이 발행되어도 `initializeScannedCandidate`는 확인한 기존 후보를 보존하고 현재 버전까지 접수한다. 프로젝트 행 잠금과 baseline별 중복 방지 키를 사용한다. 이전에 수신한 대기 작업이 있으면 이른 버전부터 처리 대상으로 남긴다. bootstrap 자체는 발행 Outbox를 새로 조작하거나 동기화 완료로 표시하지 않는다.

페이지별 후보 조회는 전역 스냅샷이 아니며 archived 프로젝트도 포함한다. 보관 프로젝트 포함 여부와 시스템 주체의 프로젝트 접근 권한은 운영 전 합의가 필요하다. 이 내부 서비스는 접근 제어된 외부 API가 아니다. 현재 구현은 자동 스케줄러가 없다.

사용자 결정에 따라 프로젝트별 baseline 버전이 1부터 연속 증가한다는 가정으로 처리 순서를 관리한다. 발행 서비스가 이 가정을 실제로 보장하는지 담당자 검토가 필요하다. 더 이른 순서의 누락이나 실패는 뒤의 업무 완료로 바꾸지 않는다. 이미 cursor를 지난 늦은 이벤트는 `RECONCILE`로 보존하고 프로젝트를 차단한다. `recoverUnattemptedReordering`은 실행 시도가 없는 순서 뒤바뀜만 복구한다. 유효한 실행 lease가 있으면 기다리고, 만료된 lease나 이미 시도된 작업은 외부 부작용 가능성 때문에 차단을 유지해 수동 재구축 대상으로 돌린다. 이 내부 연산을 호출할 권한 있는 운영 API와 수동 재구축 절차는 아직 없다.

처리 큐는 초기 시도 1회와 재시도 최대 3회를 기록하고 실패 간격은 1·5·30초다. 네 번 모두 실패하면 `FAILED`로 보존하며 동일 프로젝트의 뒤 작업은 대기한다. 명시적 재시도는 새 재시도 cycle을 시작한다. lease가 만료되면 시도 실패로 기록하고 이전 lease 소유자의 결과는 허용하지 않는다. 오류 코드는 원문이 아닌 제한된 식별자만 저장한다. 이 큐 연산은 명시적으로 호출할 때만 동작하며 실제 영향 분석이 실행됐다는 뜻이 아니다.

## 안전 경계와 추가 작업

- 이미 발행됐으나 Outbox가 없던 과거 baseline은 별도 bootstrap 후보가 필요하다. Debezium을 `initial` snapshot으로 바꾸는 것만으로 존재하지 않는 과거 Outbox가 만들어지지는 않는다.
- 프로젝트별 row lock은 현재 baseline 읽기와 **같은 잠금을 사용하는** 발행을 직렬화한다. 커넥터·checkpoint 활성화 전 커밋의 누락을 해결하지 않는다. CDC가 먼저 활성화된 조건에서 B1 후보 조회 뒤 B2가 발행되고 먼저 수신되는 경계를 같은 테스트 DB와 실제 Debezium·Kafka로 검증했다. 다만 CDC checkpoint 활성화 확인과 미완료 스캔의 재개를 자동 보장하지 않으므로 운영 초기 적재 완료를 증명하지 않는다.
- 실제 발행 서비스의 잠금·연속 version 보장과 #200 발행 이벤트, #197 사후 분석 단일 접수, #167 서비스 권한·관계 리비전, #188 분석 계약은 담당자와 조율 및 연동 전이다. CDC가 관계를 승인하거나 확정하지 않는다.
- 초안과 파싱 상태 변경은 발행 동기화의 후속 처리 대상으로 삼지 않는다. 이 사용자 결정과 현재 Jira #225의 문서 변경 캡처 보완 범위를 팀과 조율해야 한다.
- `PublicationSnapshotVerifier`는 수신된 event ID와 같은 DB의 원본 Outbox, 전후 기준·프로젝트·제안·항목 버전의 일부를 반복 가능 읽기로 대조한다. Outbox가 없으면 `UNVERIFIED`, 다르면 `INVALID`, 현재 기준이 더 바뀌었으면 `STALE`이다. 이 검증은 별도의 수동 호출이며 bootstrap으로 생성된 Outbox 없는 작업에 그대로 적용할 수 없다. 정상 후보도 문서·관계가 미검증이고 AI를 실행하지 않았으므로 실행 승인으로 취급하면 안 된다. 실제 처리·저장 시 최신성 및 동시 변경을 다시 검사해야 한다.
- 같은 격리 PostgreSQL을 source와 BE가 공유하는 스냅샷 경계 실험은 테스트 fixture로 발행을 재현했다. 후속 발행 API 전체 경로, 브로커/DB 장기 장애·복구, 멀티 파티션 순서와 운영 보안은 검증하지 않았다.
