# CDC project-key ordering experiment

This standalone fixture checks transport ordering only. It uses a test table and local PostgreSQL, Debezium and Kafka; it is **not** the #197 intake schema or production integration. Run from the repository root with Docker Desktop running:

```powershell
python infra/cdc-poc/project-ordering/run.py
```

The runner refuses to start if its own Compose project already has containers. It uses localhost Connect port 18087, no externally exposed Kafka/PostgreSQL port, and creates an isolated connector, slot and topic per run. Each run deletes only its own verified connector and inactive replication slot before stopping/removing its `beez-cdc-ordering-test` containers and network. Cleanup failures cause a nonzero exit and must be investigated before retrying. It does not delete volumes (`down` without `-v`); test topics and rows can accumulate. Earlier failed runs may have left connectors or slots and are not automatically removed. No project or production data is read or changed.

The test creates an explicit 3-partition, non-compacted topic, configures Debezium `message.key.columns` to project_id (separate from the row primary key), and inserts four sequential versions for each of twelve projects into the test table. It reads every partition independently and checks the Kafka JSON key, the actual source project and observed partition, the presence and order of each project's versions, and that at least two distinct partitions were exercised. It prints the partition mapping and fails on bad/missing ordering. All changes are committed inserts after connector startup; no background application worker is run.

Kafka ordering applies within a partition in the order records are appended. It does not by itself guarantee downstream worker start or completion order, sequence continuity, exactly-once processing, or order across topics. Multiple consumers in the same group can process different partitions concurrently; an asynchronous consumer may complete two events out of order. A consumer still needs the agreed project ordering and atomic claim/fencing rules. Changing the topic partition count can remap the same key; plan and test a migration before doing so. The project key only selects a partition; it is not an event identifier or an idempotency key. Distinct versions for a project intentionally share it, so consumer deduplication must use a separate stable event/row identifier. Since project_id is intentionally non-unique, log compaction by this key would discard previous versions; this fixture explicitly uses `cleanup.policy=delete` and production retention/compaction must be reviewed.

Not tested: #197 table/transactions, real analysis status or workers, row updates/deletes or replica identity, failed broker/connector restarts and offset redelivery, partition-count migration, TLS/SASL, multiple brokers, or production resource limits. The connector configuration is a test configuration using local-only credentials.


The runner prints the generated connector and slot names at startup. Normal exceptions attempt cleanup before Compose shuts down, including when connector registration may have succeeded but the response was lost. If a registration response is lost and the connector is not observable, it fails closed rather than assuming cleanup succeeded. It verifies the connector configuration and waits for the logical slot to become inactive; it fails rather than dropping an active or mismatched slot. If the process or machine is forcibly terminated, its `finally` cleanup cannot run. In that case, a later run does not delete unknown previous resources. Inspect only the printed names in the isolated Compose project and ask the test owner to remove that connector and inactive slot after verifying ownership. Do not delete unrelated connectors, slots, or volumes.
